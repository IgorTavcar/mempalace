Overview

System Architecture

The component map, the wake-up stack, and the non-negotiable design principles.

MemPalace is a multi-layer AI memory system built on a pluggable storage backend (ChromaDB by default) plus a SQLite knowledge graph. User data flows through three miners into verbatim drawers, indexed by AAAK-compressed closets. The L0–L3 wake-up stack injects context on demand: identity plus an essential story (~600–900 tokens), on-demand wing/room retrieval, and deep semantic search. Every component is shaped by five non-negotiable principles — verbatim-always storage, append-only ingestion, local-first execution, background hooks (zero chat interruption), and privacy by architecture (no external API required for core operations).

How it works

The system has three concerns: getting data in (ingestion), getting it out (search and the wake-up stack), and the substrate that holds it (the storage backend and knowledge graph). Each is built to honor the same invariants, so accuracy degrades gracefully rather than corrupting.

Ingestion pipeline: mine → store → index

Three miners (projects, conversations, and documents) scan source files, split content into verbatim chunks (drawers), detect entities and rooms/wings, and route each drawer to palace storage. For every drawer, the system builds AAAK-compressed closet pointers (topic + entities + quotes) so semantic search can locate relevant drawers quickly. All writes are append-only: a re-mine locks the source file, deletes prior stale drawers, then inserts fresh ones — so a crash mid-cycle leaves the palace untouched.

  • miner.py orchestrates: project files → wing/room routing → chunk → drawer storage.
  • palace.py owns closet generation (build_closet_lines): entities, topics, and quotes extracted with i18n support.
  • Drawers are stored in the mempalace_drawers collection; closets in mempalace_closets — a separate, queryable index.

Search: hybrid vector + BM25 ranking

When a query arrives, search_memories runs a hybrid strategy: closets are scanned for weak semantic signals (a similarity boost), vector embeddings search the full drawers collection, and BM25 keyword matching re-ranks the candidates. If vector search is disabled, a BM25 fallback scans ChromaDB's SQLite FTS5 layer directly. Results are always verbatim drawer text with metadata (wing, room, source file, similarity) — no summaries, no paraphrasing. Wing/room filters narrow the candidate pool at query time. See Search & Retrieval for depth.

  • Closets are ranking signals, never gates — a weak closet can only help, never hide a drawer.
  • BM25 uses local corpus IDF, so terms that discriminate within the result set bubble up.
  • Distance thresholds (max_distance, min_similarity) let callers enforce quality floors.

Wake-up stack: L0 → L1 → L2 → L3

On cold-start or conversation reset, the stack injects L0 (user identity from ~/.mempalace/identity.txt) plus L1 (an auto-generated essential story from the highest-weight drawers). This costs ~600–900 tokens and leaves 95%+ of the context window free. When a topic (wing) or old conversation (room) surfaces, L2 loads on-demand filtered retrieval. For vague queries (“remember when we discussed…”), L3 runs deep semantic search across the full palace. Each layer loads on demand and never blocks the chat; background hooks sync new memory asynchronously. The four layers are the primary external interface.

  • L0 is user-written identity text; Layer0 reads ~/.mempalace/identity.txt once per wake-up.
  • L1 scores drawers by importance + recency, groups by room, and truncates to MAX_CHARS (3200).
  • L2 retrieves up to 10 drawers filtered by wing/room metadata; L3 runs the full semantic query.

Storage backend: pluggable RFC 001 interface

The backend ABC (backends/base.py) defines the contract: get_collection() returns a collection handle, query() does semantic search, get() returns raw drawers, and upsert() writes with batching. ChromaBackend (the default reference implementation) wraps ChromaDB's PersistentClient with HNSW tuning, segment health checks, and Windows file-locking. Embeddings are computed locally (Ollama, LM Studio, …) by default; external providers (Anthropic, OpenAI) are optional and BYOK-only. New backends subclass BaseBackend and implement the same collection interface.

  • RFC 001 defines typed results (QueryResult, GetResult) that replace Chroma's raw dict shape.
  • ChromaBackend injects _HNSW_BLOAT_GUARD tuning at collection creation to prevent segfaults on large mines.
  • Lifecycle: open (lazy, on first access) → query/get/upsert → close (explicit or context exit).

Knowledge graph: temporal entity relationships

A separate SQLite database (default ~/.mempalace/kg.db) stores (subject, predicate, object, valid_from, valid_to) triples. The design is entity-first: people matter more than topics. When a drawer is filed, the KG can be seeded with facts (e.g. “Alice is Bob's partner”). Queries support temporal filtering — “who was Alice's partner on 2025-01-15?” returns only triples where valid_from ≤ date ≤ valid_to. Invalidation marks triples as ended without deletion, giving an append-only audit trail. See the Temporal Knowledge Graph page.

  • Entity IDs are SHA256(name), so queries are case-insensitive and collision-resistant.
  • Temporal format is YYYY-MM-DD or ISO UTC datetime; comparison is lexicographic in SQL.
  • Triples are immutable: facts are added, ended, or replaced — never mutated in place.

Key concepts

Wing
A broad category (person, project, topic) that groups related memory. Drawers are organized under wings.
Room
A time- or topic-based grouping within a wing (a day, a session, a discussion thread). Drawers live in rooms.
Drawer
A single chunk of verbatim user content (never summarized or paraphrased). The atomic storage unit that is queried, ranked, and returned in search results.
Closet
A searchable index layer using AAAK compression. Stores topic pointers, entity names, and quote fragments — scanned by an LLM to identify relevant drawers without reading all content.
AAAK dialect
A lossy symbolic compression format (entities, topics, emotions, flags) that lets an LLM scan thousands of closet entries instantly and know exactly which drawer to open.
L0–L3 wake-up stack
Four memory layers: L0 (user identity), L1 (essential story auto-generated from the palace), L2 (on-demand wing/room retrieval), L3 (deep semantic search). L0+L1 inject ~600–900 tokens; L2/L3 add context on demand.
Backend
A pluggable storage interface (base.py). ChromaDB is the default reference implementation; custom backends subclass BaseBackend and BaseCollection.
Knowledge graph
A SQLite-backed temporal entity-relationship graph. Stores (subject, predicate, object) triples with valid_from/valid_to dates for entity-first reasoning.

Implementation highlights

Per-palace lock: non-blocking concurrency

mine_palace_lock is keyed per palace (not global), so concurrent mines against the same palace can't corrupt the HNSW graph. It is non-blocking: if another mine holds the lock, it raises MineAlreadyRunning instead of waiting. It is re-entrant — the same thread can acquire it multiple times (e.g. ChromaCollection.upsert acquires internally). It is Windows-safe (uses msvcrt.locking on byte 0; Unix uses fcntl.flock), and the lock holder's identity is recorded in the file body for diagnostic messages.

palace.py:589 · per-palace non-blocking lock with re-entrancy and holder identity
@contextlib.contextmanager
def mine_palace_lock(palace_path: str):
    """Per-palace non-blocking lock around the full `mine` pipeline."""
    lock_dir = os.path.join(os.path.expanduser("~"), ".mempalace", "locks")
    os.makedirs(lock_dir, exist_ok=True)
    resolved = os.path.realpath(os.path.expanduser(palace_path))
    palace_key = hashlib.sha256(os.path.normcase(resolved).encode()).hexdigest()[:16]

    if _held_by_this_thread(palace_key):
        yield  # Re-entrant: same thread, same palace — pass through
        return

    try:
        fcntl.flock(lf, fcntl.LOCK_EX | fcntl.LOCK_NB)
        _write_lock_holder(lf)  # Record PID + argv for diagnostics
        _mark_held(palace_key)
        yield
    finally:
        _mark_released(palace_key)
⚠️ Gotcha

Re-entrancy is tracked in a per-thread threading.local() set of lock keys (palace.py:509). When a process forks, that set is inherited, but a PID check clears stale state so children correctly re-acquire. This prevents self-deadlock when miner.mine() (holding the outer lock) calls ChromaCollection.upsert() (trying to acquire the same lock) from the same thread.

⚡ Performance

When a mine holds the lock, the lock file body records the PID and the first three argv entries — e.g. PID 12345 mempalace mine ~/palace (palace.py:570). A contending mine reads this identity and embeds it in the MineAlreadyRunning error, so users see exactly which process is blocking them instead of a generic “locked” message.

Wake-up stack: lazy load + token budget

MemoryStack.wake_up() returns L0 (identity) + L1 (essential story) in ~600–900 tokens. L1 generation is defensive: it scans up to MAX_SCAN=2000 drawers, scores by importance metadata (with fallbacks to emotional_weight and weight), sorts, groups by room, and truncates to MAX_CHARS=3200. If the importance field is absent it defaults to 3.0. Token estimates use len(text)//4 (conservative; actual tokens may vary).

layers.py:381 · wake-up stack — L0 + L1 injection
def wake_up(self, wing: str = None) -> str:
    """
    Generate wake-up text: L0 (identity) + L1 (essential story).
    Typically ~600-900 tokens. Inject into system prompt or first message.
    """
    parts = []
    # L0: Identity
    parts.append(self.l0.render())
    parts.append("")
    # L1: Essential Story
    if wing:
        self.l1.wing = wing
    parts.append(self.l1.generate())
    return "\n".join(parts)
💡 Insight

Layer1.generate() tries four metadata keys in order — importance, emotional_weight, weight — defaulting to 3.0 if none are found (layers.py:129). This gives backward compatibility with older schemas and multiple naming conventions. With no importance field at all, every drawer is weighted equally and ranked only by fetch order.

AAAK closet pointers: i18n-aware entity extraction

build_closet_lines() extracts entities from drawer content using i18n-aware regex patterns (loaded from locale JSON via entity_detector). Entities must occur at least twice in the window. A stoplist filters common English filler (The, This, When) and COCA vocabulary words so fake entities don't pollute closets. The legacy format is topic|entities|→drawer_ids; the Tier 6a format adds dates and line numbers as topic|entities|YYYY-MM-DD:Lstart-Lend|→drawer_ids when metadata is available.

def build_closet_lines(source_file, drawer_ids, content, wing, room, drawer_metas=None):
    """Build compact closet pointer lines from drawer content."""
    drawer_ref = ",".join(drawer_ids[:3])
    coca_filter = _get_coca_filter()          # Common English content words
    words = _candidate_entity_words(window)   # i18n-aware patterns

    # Entities must occur >=2 times
    word_freq = {}
    for w in words:
        if w in _ENTITY_STOPLIST:             # Filter The, This, When, etc.
            continue
        if w.lower() in coca_filter:
            continue
        word_freq[w] = word_freq.get(w, 0) + 1

    entities = sorted(
        [w for w, c in word_freq.items() if c >= 2],
        key=lambda w: -word_freq[w],
    )[:5]  # Top 5 entities
⚡ Performance

Closets pack greedily up to CLOSET_CHAR_LIMIT=1500 chars, but lines are never split (palace.py:149). If a line would overflow the current closet, it flows to a new one (_01, _02, …). This keeps closet pointers grep-friendly and atomic, so an LLM can parse a single line without worrying about continuations.

ChromaBackend: HNSW bloat guard

New collections are created with _HNSW_BLOAT_GUARD tuning — hnsw:batch_size=50_000 and hnsw:sync_threshold=50_000 (backends/chroma.py:101). This defers persistence until a large batch completes, breaking the resize+persist feedback loop that caused link_lists.bin to balloon to hundreds of GB on large mines. It was empirically validated on a 39k-drawer rebuild: palace 376 MB, link_lists.bin 0 bytes, and no segfault.

Hybrid search: BM25 + vector rerank

search_memories() queries ChromaDB's vector API, gets candidate drawers, computes Okapi-BM25 scores locally over the candidate set's corpus IDF, then reranks. If vector search is disabled, it falls back to ChromaDB's SQLite FTS5 layer, scoring with BM25. Closets contribute an optional closet_boost_weight — never a gate — so weak closets can't hide strong BM25 matches.

💡 Insight

BM25 IDF is computed over the candidate set returned by vector search, not the full palace (searcher.py:75). This is exactly right for reranking a small set: a term rare in the full palace but common among the candidates gets an inflated IDF, which is precisely what discriminates within those results. Applied to the full palace, the same math would be inaccurate.

Design decisions

Append-only writes with atomic delete+insert per file
Incremental-only principle (CLAUDE.md line 23): never destroy existing data to rebuild. Re-mines lock, delete stale drawers for that source_file, then insert fresh ones. A crash during delete leaves drawers with a stale normalize_version (re-mined later); a crash during insert leaves the old drawers intact. Either way, no palace corruption.
Closets as optional ranking boost, never as gates
100% recall is non-negotiable. Weak closets (regex-extracted from narrative content) must never hide drawers. Only BM25 + vector distance decide inclusion; closets add a boost weight. If entity extraction fails or closets are stale, search accuracy degrades gracefully.
L0+L1 wake-up automatic, L2+L3 on-demand
Performance budgets (CLAUDE.md line 26): hooks <500ms, startup injection <100ms. Inject minimal context (identity + essentials) automatically; load deeper context (wings, topics, searches) only when the user mentions them, leaving 95%+ of the context window free.
Local-first embedding + optional external LLM
Local-first, zero external API by default (CLAUDE.md line 25): embeddings run on Ollama/LM Studio on localhost. External providers (Anthropic, OpenAI, Google) are BYOK, never required, never silent. Code explicitly checks for configured providers before any fallback, so external APIs are never enabled by environmental surprise.
Per-palace locking, non-blocking, with identity recording
Concurrency safety without resource exhaustion. Per-palace (not global) allows parallel mines on different palaces; non-blocking prevents daemon pileup; identity recording lets users diagnose the holder; thread + PID tracking prevents self-deadlock when nested miners try to re-acquire.
🔒 Security

The MCP server redirects stdout→stderr at both the Python and file-descriptor level before importing chromadb/onnxruntime (mcp_server.py:22), because those dependencies print banners and errors straight to stdout (sometimes at the C level), which would break Claude Desktop's JSON-RPC parser. The real stdout FD is saved and restored before the protocol loop so valid JSON-RPC goes to stdout and debug logs to stderr. See MCP Server & Tools.

💡 Verbatim always

No summarization, paraphrasing, or lossy compression of drawer content. CLAUDE.md (line 22) is explicit: “If a user said it, we store exactly what they said.” This extends to whitespace, code formatting, and even Unicode surrogate pairs (handled by strip_lone_surrogates for Windows clipboard corruption). See Surprises & Gotchas and Security & Privacy.

Data flow

Data enters through three miners: project (code/docs), conversation (transcripts), and documents (binary office files). Each miner reads source files, splits them into verbatim chunks (drawers), detects wings/rooms and entities, and routes them to the palace. For each drawer, palace.py builds AAAK-compressed closet pointers (entities, topics, quotes, dates, line numbers). Drawers land in the mempalace_drawers collection; closets in mempalace_closets.

On search, searcher.py queries via the hybrid path (vector + BM25 rerank), optionally boosted by closet hits, returning verbatim drawer text. On context injection, layers.py generates L0 (identity from ~/.mempalace/identity.txt) + L1 (top drawers by importance + recency). The KnowledgeGraph (SQLite) stores entity-relationship triples seeded from drawer facts, enabling entity-first temporal queries. All writes are append-only (lock, delete stale per source_file, insert fresh), and background hooks sync new content invisibly.

The append-only crash matrix
  • Crash during delete: old drawers still exist but may carry a stale normalize_version — file_already_mined() flags them for a later re-mine. No data lost.
  • Crash during insert: the new drawers are missing, but the old ones remain queryable. No data lost.
  • Concurrent mine: mine_palace_lock raises MineAlreadyRunning with the holder's PID+argv rather than waiting or corrupting the HNSW graph.
