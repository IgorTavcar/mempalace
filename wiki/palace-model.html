Overview

The Palace Model

Method-of-loci + Zettelkasten mapped onto concrete data structures.

The Palace Model is MemPalace's spatial memory architecture. Wings (people/projects) contain Rooms (days/topics), which hold Drawers — immutable ~800-char chunks of verbatim source text. A compact index layer of Closets stores topic/entity/quote pointers that lead searchers to drawers. Hallways connect entities within a wing; Tunnels link rooms across wings. A living-connection Dynamics layer (Hebbian strength + Ebbinghaus decay) makes those connections fade or strengthen based on actual use, and Tier 6a dating gives every memory a temporal scope.

How it works

A palace is a tree. The miner walks a directory, normalizes the folder name into a wing, detects a room from the file path/keywords, chunks the content into drawers, and upserts them. In parallel it extracts closet pointers for fast search, computes within-wing hallways from entity co-occurrence, and links wings with cross-wing tunnels. The whole structure is built to be re-mined safely: IDs are deterministic, dedup is symmetric, and accumulated connection salience survives a rebuild. See project mining and conversation mining for the ingestion side, and search for the retrieval side.

Spatial organization — wings, rooms, drawers

Each drawer holds ~800 chars of original text and is identified by a deterministic SHA256 hash of source_file + chunk_index, wrapped as drawer_WING_ROOM_hexsuffix. Metadata tags every drawer with its wing, room, source file, chunk index, filed_at (ingestion time), hall (detected via keyword regex), entities (capitalized words appearing ≥2 times), and optionally content_date, line_start, and line_end (Tier 6a) for precise source location.

Closets — the searchable index

Closets are compact pointers extracted during mining. The builder reads the first 5,000 chars of a drawer and emits atomic pointer lines: topics (pattern-matched from action verbs like built, fixed, wrote and section headers), double-quoted spans, and capitalized entity pairs that co-occur 2+ times (deduplicated, ranked by frequency, top 5 per pointer). Lines are then packed greedily into closet documents up to 1,500 chars without ever splitting a line. Closets connect to the AAAK dialect, the symbolic format that lets LLMs scan the index efficiently.

Hallways — within-wing entity connections

When a wing is mined, the system scans its drawers and computes hallways from entity co-occurrence. For each pair of distinct entities appearing together in 2+ drawers, a hallway record (id = hash of wing + sorted entity pair) tracks the pair, co-occurrence count, and the rooms where they were seen together. Hallways are persisted in hallways.json with a living-connection layer. Because IDs are symmetric (sorted pair), a re-computed hallway upserts the existing record rather than creating duplicates.

Tunnels — cross-wing links

Tunnels are symmetric connections between two wing/room endpoints, in three flavors:

  • Explicit — user-created via MCP/CLI, linking specific rooms (e.g. auth relates to users).
  • Topic — auto-generated when two wings share 1+ confirmed topics; uses synthetic room ids like topic:Angular.
  • Entity — auto-generated from hallway data when the same entity appears in both wings; uses entity:Ben.

All tunnels live in tunnels.json, deduplicated by canonical ID (hash of sorted endpoints), and carry living-connection dynamics. See the temporal knowledge graph for the complementary semantic/temporal edge store.

Dating and temporal scope (Tier 6a)

Each drawer stores three temporal fields: filed_at (ingestion timestamp), content_date (extracted from filename, frontmatter, or mtime as ISO YYYY-MM-DD), and optionally line_start/line_end (1-indexed source line numbers). Closet pointers can splice in a Tier 6a date+line segment (YYYY-MM-DD:Lstart-Lend) so a search jumps straight to the right span. When content_date is present it is preferred over filed_at for the dating hierarchy. Diaries (conversation transcripts) extract dates from ISO patterns in filenames, enabling temporal grouping of related talks.

Dynamics — living connections with decay

Both hallways and tunnels carry four dynamics fields: strength (Hebbian weight, 0.05–5.0), stability (decay resistance), last_activated, and access_count. Hebbian potentiation grows strength by 0.05 per access (capped at 5.0). Ebbinghaus decay fades it over time (new = old · exp(-days_since / stability)), floored at 0.05 so connections never reach zero. The Cepeda spacing effect means stability only grows when reinforcement is spaced more than an hour apart — rapid bursts don't build durability.

💡 Two-layer index by design

Closets are not one-pointer-per-record — pointer lines are batched greedily into numbered closet documents (closet_base_01, closet_base_02, …) up to the char limit. The same source file produces the same closet numbering deterministically. This mirrors the Zettelkasten split: small index cards (closets) that point to larger content (drawers), so search hits the tiny index first and only fetches the drawers it needs.

Key concepts

Wing
A named broad category (person, project, department) derived from a directory name. Normalized to lowercase with underscores replacing hyphens and spaces. Drawers tagged with a wing can be filtered, scoped, or tracked as a unit.
Room
A time- or topic-based grouping within a wing (e.g. diary, meetings, design-docs). Detected from file paths, filenames, or keywords during mining. Rooms span multiple wings via Tunnels.
Drawer
A chunk of verbatim source text (~800 chars), immutable once written. Identified by drawer_WING_ROOM_SHA256(source-file + chunk-index). Stores original content, entities, halls, dates, and line numbers.
Closet
A searchable index record (in the mempalace_closets collection) containing compact topic/entity/quote pointer lines that reference one or more drawers. Built during mining by extract→pointer→pack logic; packed greedily up to 1,500 chars per closet.
Hallway
A within-wing connector materializing entity-pair co-occurrence. If entities Aya and Lumi appear together in 2+ drawers of the same wing, a hallway records the pair, count, and rooms where they co-occurred. Persisted in hallways.json.
Tunnel
A cross-wing link between two rooms (or synthetic topic:/entity: rooms). Explicit tunnels are user-created; topic and entity tunnels auto-generate when shared topics or entities are detected across wings. Persisted in tunnels.json.
Diary
A dated journal entry or conversation log mined from a transcript file. The timestamp (ISO YYYY-MM-DD) is extracted from the filename, frontmatter, content, or mtime and stored as content_date in drawer metadata, enabling temporal grouping.
Dynamics
Living-connection math: Hebbian potentiation (strength grows on co-access), Ebbinghaus decay (fades over time), and the Cepeda spacing effect (stability grows on spaced reinforcement). Applied identically to hallways and tunnels to rank by salience.

Implementation highlights

Drawer ID scheme

Drawer IDs are a deterministic SHA256 of the source file path plus chunk index, truncated to 24 hex chars. A re-mined file at the same path with the same chunks produces identical IDs, enabling safe upsert (miner.py:1247).

miner.py:1247 · deterministic, idempotent drawer ID
drawer_id = f"drawer_{wing}_{room}_{hashlib.sha256((source_file + str(chunk_index)).encode()).hexdigest()[:24]}"

Closet pointer line format

Pointers come in two formats: legacy 3-segment (topic|entities|→drawer_ids) and Tier 6a 4-segment with an optional date+line span. The builder emits the 4-segment form when line numbers and a date are available and falls back to 3-segment otherwise, so old and new pointers coexist in one collection (palace.py:304).

palace.py:304 · backward-compatible pointer emission
def _pointer(prefix: str) -> str:
    if date_line_seg is not None:
        return f"{prefix}|{entity_str}|{date_line_seg}|→{drawer_ref}"
    return f"{prefix}|{entity_str}|→{drawer_ref}"

Greedy closet packing

Closets accumulate pointer lines up to CLOSET_CHAR_LIMIT (1,500 chars), flushing to a numbered closet when the next line wouldn't fit. Lines are never split; an oversized line opens a new closet. This greedy packing is a compact alternative to exact bin-packing (palace.py:149, palace.py:377).

Hebbian potentiation with spacing

On a co-access event strength grows by the increment (capped at MAX_STRENGTH), but stability only grows when the reinforcement is spaced at least an hour from the last activation (dynamics.py:143).

dynamics.py:143 · Hebbian growth + Cepeda spacing gate
if hours_since >= SPACED_INTERVAL_HOURS:
    current_stability = float(connection.get("stability", DEFAULT_STABILITY))
    connection["stability"] = current_stability + STABILITY_INCREMENT
current_strength = float(connection.get("strength", DEFAULT_STRENGTH))
connection["strength"] = min(MAX_STRENGTH, current_strength + float(increment))

Ebbinghaus decay

dynamics.py:193 · exponential decay floored at STRENGTH_FLOOR
days_since = (now - last_dt).total_seconds() / 86400.0
stability = float(connection.get("stability", DEFAULT_STABILITY))
if stability <= 0:
    stability = DEFAULT_STABILITY
current_strength = float(connection.get("strength", DEFAULT_STRENGTH))
decay_factor = math.exp(-days_since / stability)
new_strength = current_strength * decay_factor
connection["strength"] = max(STRENGTH_FLOOR, new_strength)
⚠️ Dynamics must survive a re-mine

When a hallway or tunnel is recomputed on a fresh mine, the code explicitly copies the prior record's strength, stability, last_activated, and access_count before initializing any missing fields (hallways.py:256). Without this, every mine would reset connection weights to defaults and wipe accumulated salience — a subtle but critical detail for the living-connection layer.

💡 Synthetic room prefixes namespace auto-tunnels

Auto-generated topic and entity tunnels don't link literal rooms; they use synthetic identifiers like topic:Angular and entity:Ben (palace_graph.py:723). This keeps a wing's literal Angular folder room distinct from an Angular topic tunnel, and the prefix is visible to LLMs scanning the tunnel list, making the distinction machine-readable.

Edge cases & details
  • Immutable content, mutable metadata. Once a drawer's content is written it never changes. Re-mining a file deletes the old drawers for that source_file and writes new ones; metadata (entities, hall, content_date) can be updated on upsert, but the verbatim content block is frozen (palace.py:365). This matches the "incremental only" principle: never destroy data to rebuild.
  • Graph cache TTL. palace_graph.py keeps a module-level cache of the computed graph with a 60-second TTL and write-invalidation, so build_graph() serves repeated reads from cache and is invalidated via invalidate_graph_cache() (palace_graph.py:60).
  • Wing normalization at the boundary. normalize_wing_name() lowercases and replaces hyphens/spaces with underscores at both write and read time, so mempalace-public and mempalace_public resolve to the same wing (config.py:34).
⚡ Cached graph reads

build_graph() traverses drawer metadata to build room nodes and cross-wing edges, then serves subsequent reads in O(1) from a 60-second cache, invalidating only on writes (palace_graph.py:60, palace_graph.py:90). Repeated traversal and stats calls stay cheap.

Design decisions

Drawers are content chunks; closets are the index.
Splitting content into ~800-char drawers avoids embedding whole files and allows fine-grained retrieval. Closets point to drawers, so search hits small index documents first and only fetches the drawers it needs — a two-layer design matching the Zettelkasten principle.
Wing names are normalized at the boundary.
Lowercasing and collapsing separators at write and read time makes mempalace-public and mempalace_public resolve to the same wing, reconciling hyphenated directory names with underscored YAML slugs while keeping user input flexible.
Topic/entity tunnels use synthetic room prefixes.
Prefixing auto-generated tunnels with topic:/entity: keeps them from colliding with literal folder-derived rooms, keeps the graph clean, and makes real-room traversals easy to distinguish from topical links.
Hallways and tunnels preserve dynamics across re-mines.
Accumulated salience (strength, stability, access_count) is the lived history of a connection. Preserving these fields and re-initializing only missing ones keeps a durable memory of which connections matter most.
Closets are built greedily, not bin-packed; lines never split.
Greedy packing is simpler to reason about than optimal bin-packing while staying compact. Atomic, self-contained pointer lines reduce partial matches and keep the index format clean.

Data flow

Data flows from source files into drawers during mining: the miner reads a file, chunks it, extracts entities/hall/date metadata, builds drawer records (wing_ROOM_hash), and upserts them to the mempalace_drawers collection. Simultaneously, closet pointers (topics, entities, quotes) are extracted from the first 5,000 chars and packed into closets, upserted to mempalace_closets. Within-wing hallways are computed from drawer entity metadata via co-occurrence counting (pairs appearing 2+ times) and persisted to hallways.json, preserving prior dynamics. Cross-wing tunnels are explicit (user-created via MCP), auto-generated from topic overlaps (compute_topic_tunnels), or inferred from hallway entities (entity_tunnels_for_wing), all stored in tunnels.json with symmetric dedup.

On search, queries hit mempalace_closets first to find relevant closet documents, parse them to extract drawer IDs, then fetch those drawers from mempalace_drawers and rank by distance. If no closets match, search falls back to direct drawer search. The palace_graph module builds a cached in-memory graph from drawer metadata (rooms as nodes, wing-spanning rooms as edges/tunnels) for traversal and statistics, invalidating the cache on every write. See the system architecture for how these collections sit in the broader pipeline and storage backends for where they persist.
