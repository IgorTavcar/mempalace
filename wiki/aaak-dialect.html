AAAK Dialect & Closets

A compact symbolic index an LLM can scan in one pass to know which drawer to open.

AAAK is a lossy summarization format that extracts entities, topics, key quotes, emotions, and importance flags from verbatim drawer content into a single compact line (typically 40–150 bytes). Closets are searchable index collections that hold these pointer lines, each pointing back to the original drawer(s) via the → syntax. During retrieval, the searcher scans closets to identify relevant drawers, then returns verbatim content from the drawers themselves — 100% recall is preserved because no information is lost, only indexed. The dialect handles non-Latin scripts (Hindi, Cyrillic, Arabic…) through language-aware Unicode patterns in the i18n system.

How it works

In the palace model, drawers hold verbatim 800-character chunks of your content; closets are a thin index on top of them. AAAK is the dialect that turns a drawer into a closet line. Think of it as the Zettelkasten index card layer: small, cross-referenced cards (closets) point to larger source materials (drawers), and the card is scannable in a single LLM context window.

Encoding: from drawer to closet line

When a file is mined (see project mining), drawers are created and indexed. For each drawer, build_closet_lines() (palace.py:241) extracts topics (action verbs and headers via regex), entities (proper nouns appearing 2+ times, using i18n-aware patterns), and quotes (double-quoted strings). Each topic, quote, and summary becomes one atomic line such as built auth system|Ben;Igor|→drawer_api_auth_a1b2c3. Lines are packed greedily into closets; when adding a line would exceed 1500 chars the closet rolls to a new number (_01, _02…) and a single line is never split across closets.

  • Topics extracted via action-verb regex: built|fixed|wrote|added|pushed|deployed…
  • Entities: 2+ occurrences in the 5000-char extraction window, sorted by frequency, capped at 5
  • Quotes: double-quoted strings 15–150 chars, up to 3 per closet
  • Closet size capped at 1500 chars; lines never split across closets
  • Entities filtered against a hardcoded stoplist and the COCA corpus to drop false entities

Dialect compression: plain text to AAAK

Dialect.compress() (dialect.py:561) turns any plain text into AAAK format by detecting emotional tone (keyword matching _EMOTION_SIGNALS), importance flags (_FLAG_SIGNALS), topics (TF-IDF plus a proper-noun boost), and a key sentence (decision-word scoring). Output is 2–4 lines: an optional header (wing|room|date|title), then a zettel line with entity codes, topics, quote, emotions, and flags. For zettel JSON files, encode_zettel() uses identical logic but reads from structured fields. The Dialect object optionally loads i18n regex patterns via get_regex() for non-Latin scripts.

  • Emotion detection: 30+ keyword mappings (love→love, feared→fear…)
  • Flag signals: 40+ keyword patterns (decided→DECISION, founded→ORIGIN…)
  • Topic ranking: TF-IDF with +2 bonus for capitalized / CamelCase / hyphenated words
  • Key sentence scoring: +2 for decision words, +1 for <80 chars, -2 for >150 chars

Closet-first retrieval: scan index, open drawer

During search, the searcher (searcher.py:841) queries closets via ChromaDB embedding similarity in parallel with the raw drawer query. For each top closet hit it parses the →drawer_id_a,drawer_id_b pointer (searcher.py:180) to learn which drawers are relevant, then builds a boost lookup keyed by source_file storing (rank, distance, preview). Drawers are scored on their own vector distance, and any drawer from a source that matched a closet receives a rank-based boost: position 0 → +0.40, position 1 → +0.25, and so on, applied only when closet distance ≤ 1.5 (cosine). Boosted hits surface higher; their matched_via field becomes "drawer+closet" and a closet_preview field shows the line that matched.

  • Closets queried in parallel with drawers — no sequential gate
  • Closet boost is ordinal (rank position), not distance-based — more reliable on narrative
  • Boost capped at CLOSET_DISTANCE_CAP (1.5) to drop weak closet signals
  • Falls back to drawer-only search if closets don't exist or all hits are filtered

Non-Latin script support via i18n

The i18n module (i18n/__init__.py) provides language-specific entity patterns. For scripts with combining marks (Devanagari, Arabic, Hebrew, Thai), the locale file declares boundary_chars (Hindi: "\wऀ-ॿ"). _script_boundary() (i18n/__init__.py:113) replaces \b with a lookaround that treats those characters as “inside word.” When closets are built, _candidate_entity_words() (palace.py:215) applies these patterns from get_entity_patterns() so a Hindi name ending in a matra (ा ी) matches in full instead of being truncated at the mark. Closet entities for all scripts are extracted identically.

LLM-assisted closet refinement

Regex closets are always built during mining with zero external calls. Optionally, after mining, regenerate_closets() (closet_llm.py:206) can replace them with richer ones using a configured endpoint (Ollama, vLLM, llama.cpp, OpenAI, OpenRouter). Each source file is chunked to 30K chars and sent via an OpenAI-compatible /chat/completions call asking for JSON with topics (8–15), quotes (2–5), and a summary; the output is parsed into closet lines and written via upsert_closet_lines() after purging the old closets. See LLM integration for endpoint configuration.

  • Completely optional; core retrieval uses regex closets with zero LLM calls
  • Supports any OpenAI-compatible endpoint
  • Retries 3× with exponential backoff on 429/503; returns None silently on failure

Layer 1 generation: essential story extraction

Dialect.generate_layer1() (dialect.py:806) reads all zettel files and pulls high-weight moments (weight ≥ threshold, default 0.85) plus anything flagged ORIGIN/CORE/GENESIS. These are grouped by date into MOMENTS sections, each entry showing entity + title + quote + weight + flags, alongside identity sections, an emotional arc, and up to 8 key tunnels. The result is a wake-up summary an LLM can scan in one shot (~1.5–2.5K tokens) to know the essential story before diving into full closets.

Key concepts

AAAK Dialect
A structured symbolic summarization format extracting entities (people), topics (key phrases), quotes (5–55 char snippets), emotional tone (3 codes like vul+joy), and importance flags (ORIGIN, CORE, PIVOT) into pipe-separated lines readable by any LLM without decompression.
Closets
ChromaDB index documents (1500 chars max) holding topic pointers back to drawers. Each line is atomic: topic|entities|→drawer_a,drawer_b. Created during mining, rebuilt on re-mine, queried first during search to identify relevant drawers before fetching verbatim content.
Zettelkasten Index
Inspired by Niklas Luhmann's method: small cross-referenced index cards (closets) point to larger verbatim source materials (drawers). The AAAK format makes cards scannable in a single LLM context window, allowing semantic decisions about which drawer to retrieve without loading the drawer itself.
Lossy Summarization
AAAK extracts key signals from content (it is not compression) but preserves 100% recall because drawers hold the original verbatim text. The indexed information is a subset, but nothing is lost — the retrieval path always returns exact words from the source.
Emotion Codes
Single-letter abbreviations mapping emotional tone (vul=vulnerability, joy=joy, fear=fear…) extracted from content keywords or metadata. Up to 3 codes per line; helps LLMs prioritize emotionally significant moments during retrieval.
Importance Flags
Binary metadata tags (ORIGIN=founding moment, CORE=identity pillar, PIVOT=turning point, SENSITIVE=private) extracted from content keywords or zettel metadata to signal which drawers hold foundational or sensitive information.
Entity Stoplist
Hardcoded set of 50+ common English words that look like proper nouns but are usually sentence-starters (The, When, User) or weekday/month names. Filtered during entity extraction so fake entities don't clutter closet pointers.
Closet Boost
Hybrid retrieval optimization: when a searcher matches a closet, it boosts the ranking (up to 0.40) of drawers from that source file. Rank-based (ordinal position) rather than distance-based, since it is more reliable on narrative content where distances cluster.
i18n-aware Entity Detection
Localization system supporting combining marks (Devanagari, Arabic harakat, Thai), Cyrillic, and accented Latin. Each language declares boundary_chars to expand Python's \b regex to scripts where word boundaries aren't \w transitions. Closets in any script are extracted identically.

Implementation highlights

Lossy vs. lossless: the fundamental design

The module docstring (dialect.py:14) is emphatic that AAAK is not lossless compression — the original text cannot be reconstructed from AAAK output. It is a structured summary layer (closets) that points to the original verbatim content (drawers). Information is selected for the index, but nothing is lost because drawers hold the original words.

dialect.py:1 · the design statement, verbatim
NOTE: AAAK is NOT lossless compression. The original text cannot be reconstructed
from AAAK output. It is a structured summary layer (closets) that points to the
original verbatim content (drawers). The 96.6% benchmark score is from raw mode,
not AAAK mode.
💡 Insight — closets are a ranking signal, never a gate

The searcher always runs the full drawer query first; closets only boost results. The comment at searcher.py:823 spells out the reasoning: closets are “a ranking SIGNAL, never a first-pass filter,” deliberately avoiding the weak-closets regression where narrative content produces low-signal closets and closet-first routing hides drawers that direct search would find. 100% recall requires never hiding a drawer.

Closet boost: ordinal > distance for narrative

CLOSET_RANK_BOOSTS = [0.40, 0.25, 0.15, 0.08, 0.04] (searcher.py:871). The searcher ranks closets by ordinal position rather than absolute distance, because, as the comment explains, “closet distances cluster in 1.2–1.5 range regardless of match quality” — narrative closets have poor distance calibration, so the rank position is the more trustworthy signal.

Building closet lines

palace.py:241 · build_closet_lines() — topics, 2+ entities, quotes
def build_closet_lines(source_file, drawer_ids, content, wing, room, drawer_metas=None):
    drawer_ref = ",".join(drawer_ids[:3])
    window = content[:CLOSET_EXTRACT_WINDOW]
    words = _candidate_entity_words(window)
    word_freq = {}
    for w in words:
        if w in _ENTITY_STOPLIST:
            continue
        word_freq[w] = word_freq.get(w, 0) + 1
    entities = sorted([w for w, c in word_freq.items() if c >= 2],
                     key=lambda w: -word_freq[w])[:5]
    topics = re.findall(r"(?:built|fixed|wrote|added...)\s+[\w\s]{3,40}", window, re.IGNORECASE)
    quotes = re.findall(r'"([^"]{15,150})"', window)
    lines = [f"{topic}|{entity_str}|→{drawer_ref}" for topic in topics]
    return lines
⚡ Performance — emotion detection is keyword-based, no LLM

Plain-text emotion detection (_detect_emotions, dialect.py:430) scans for 30+ keywords in lowercase text (love→love, feared→fear, happy→joy). No ML, no API call: the result is instant, deterministic, and costs zero tokens. Only 3 codes are emitted per line and redundant codes are deduped — a fast triage signal.

🔒 Security — privacy by architecture in closet_llm

LLMConfig.__init__ (closet_llm.py:96) validates the endpoint scheme strictly: anything other than http/https raises ValueError at parse time. A misconfigured LLM_ENDPOINT with a file:// URL can never exfiltrate local files — the check runs on init, not at call time. The module also uses stdlib urllib rather than the requests library or a vendor SDK. See security & privacy.

closet_llm.py:96 · reject non-HTTP schemes at init
if self.endpoint:

    if scheme not in ("http", "https"):
        raise ValueError(
            f"LLM_ENDPOINT must use http:// or https:// (got scheme {scheme!r})"
        )
⚠️ Gotcha — regex closets have no stop-word filter

build_closet_lines() (palace.py:287) extracts topics via the action-verb regex but does not filter the matched phrases through a stop-word list, so a topic like built the the the can be extracted verbatim. The COCA filter helps with common words (Code, Line) but dialect.py's _STOP_WORDS are never applied to regex closet extraction. This is an inconsistency: dialect closets use _STOP_WORDS, while closet_llm ones are manually curated. See surprises.

Edge cases & bounded scanning
  • Extraction window. CLOSET_EXTRACT_WINDOW = 5000 (palace.py:150) — regex closets only scan the first 5000 chars of content, capping CPU cost but leaving long files with incomplete coverage. LLM closets process up to 30K chars, a key advantage.
  • Entity frequency. Entities must appear 2+ times in the window (palace.py:281); single-mention names (one-time guests) are filtered, keeping pointers focused on recurring people and projects.
  • Concurrency. mine_lock() (palace.py:418) uses fcntl on Unix and msvcrt on Windows, keyed by SHA256(source_file)[:16] + ".lock", protecting the purge+upsert closet cycle from interleaving during simultaneous LLM regeneration and regex rebuild.
  • Backward-compatible pointers. Closets support legacy 3-segment (topic|entities|→drawer) and Tier 6a 4-segment (topic|entities|YYYY-MM-DD:Lstart-Lend|→drawer) formats (palace.py:247); legacy is emitted when metadata is missing so old closets work in new code.

i18n combining-mark boundaries

_script_boundary() (i18n/__init__.py:113) replaces Python's \b with a lookaround like (?:(?<=[chars])(?=[^chars])|…). For Hindi, chars="\wऀ-ॿ" so Devanagari matras (ा ी ु) count as inside-word. This lets a name like अनीता match in full instead of truncating to अनीत. The docstring at i18n/__init__.py:116 explains why: \w covers Unicode Letter/Number categories but not Marks.

Design decisions

Closets as a selective index, not a filtered cache — always return verbatim from drawers
The CLAUDE.md principle is “Verbatim always.” Closets are pointers to verbatim content, not summaries. Selection happens at index time (which topics to extract), but nothing is lost from the drawer — guaranteeing 100% recall because the original words remain accessible.
Hybrid ranking: the drawer query always runs; closets provide a boost signal only
This prevents weak closets (common on narrative content) from hiding drawers that direct semantic search finds (searcher.py:826). Closet distance clustering (1.2–1.5) is unreliable on narrative, so ordinal rank is a better signal, and hybrid scoring ensures no perfect-recall regressions.
LLM closet regeneration is optional; regex closets are always available
The CLAUDE.md principle is “Local-first, zero external API by default.” Regex closets work offline with zero dependencies and zero tokens. LLM regeneration is an opt-in enhancement for richer indexing; the regex fallback ensures core retrieval never breaks if the LLM is unavailable.
Non-Latin scripts handled via script-aware boundaries, not post-hoc normalization
Combining marks (Devanagari, Arabic, Hebrew) are part of the script and must not be stripped. Expanding \b at regex-compile time via _script_boundary is simpler and faster than NFD-normalizing text, and patterns are cached per language tuple to amortize the cost.
Emotion codes are hardcoded keyword-based, not learned embeddings
Performance and privacy. Keyword matching is O(1); LLM calls would add latency and tokens. Codes are universal (30+ emotions mapped to 2–4 char codes), deterministic, and transparent — sufficient signal for triage without ML.

Data flow

Plain text (projects, conversations) → the miner creates drawers (800 chars each, verbatim) and calls build_closet_lines() → topics, entities, and quotes are extracted via i18n-aware regex with COCA and stoplist filtering → closet pointer lines (topic|entities|→drawer_a,drawer_b) are packed into ChromaDB closets (max 1500 chars). Optionally, LLMConfig drives regenerate_closets(), whose output replaces the regex closets with LLM-mined topics, quotes, and a summary.

On retrieval, search() queries both drawers (full embedding) and closets (the index) in parallel. Closet hits are parsed for drawer pointers, the ordinal-rank boost is applied to drawers from matching sources, and the final ranking merges vector distance with closet boost. Results carry a matched_via field (drawer, closet, or drawer+closet) and an optional closet_preview; for closet+drawer hits, _expand_with_neighbors() fetches ±radius sibling chunks for context.
