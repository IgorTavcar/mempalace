Temporal Knowledge Graph

Entity→predicate→entity facts with validity windows, stored in local SQLite and queryable by time.

The Temporal Knowledge Graph stores structured facts as subject→predicate→object triples with optional valid_from/valid_to timestamps, so you can ask what was true at a specific instant. It is built on a single local SQLite database with thread-safe WAL mode and zero external dependencies. It complements vector search by answering deterministic relationship queries (“Who was Alice’s employer in 2023?”) and acts as ground truth for fact-checking and entity disambiguation.

How it works

Storage: SQLite with WAL and thread safety

The KG lives in a single local SQLite database at ~/.mempalace/knowledge_graph.sqlite3 with Write-Ahead Logging enabled for durability and concurrent reads. A threading.Lock guards every database operation; the connection uses check_same_thread=False and a 10-second busy timeout to tolerate contention. Each KnowledgeGraph instance is a singleton per palace path, cached in mcp_server._kg_by_path so there is a single writer and consistent reads. The schema holds two tables:

  • entities — id, name, type, properties (JSON).
  • triples — subject, predicate, object, valid_from, valid_to, confidence, and provenance fields, with indexes on subject, object, predicate, and the temporal columns.

Temporal normalization: legacy date-only and canonical UTC

The KG accepts both YYYY-MM-DD (legacy) and YYYY-MM-DDTHH:MM:SSZ (canonical) formats for temporal values. To make lexicographic string comparison correct, date-only values are normalized at query time: valid_from='2026-01-01' becomes '2026-01-01T00:00:00Z', while valid_to='2026-01-01' becomes '2026-01-01T23:59:59Z'. This happens via SQL CASE expressions (_sql_temporal_start_expr, _sql_temporal_end_expr) so a query like as_of=2026-01-15T10:30:00Z still matches facts stored as date-only. _temporal_filter_sql assembles the WHERE clause: (valid_from IS NULL OR start_expr <= as_of) AND (valid_to IS NULL OR end_expr >= as_of).

💡 Insight

Date-only facts are interpreted as full-day intervals at query time. A legacy valid_from='2026-01-01' opens at T00:00:00Z and valid_to='2026-01-01' closes at T23:59:59Z, so a date is treated as a 24-hour window rather than a single point. This lets canonical UTC as_of queries match older date-only triples without a migration. See knowledge_graph.py:56.

Add, query, and invalidate operations

Adding a triple (add_triple) auto-creates missing entity nodes, normalizes the predicate, generates a unique triple_id from a hash of valid_from and the current timestamp, and validates that valid_to >= valid_from (raising ValueError on an inverted interval). Query operations (query_entity, query_relationship, timeline) apply a temporal filter when an as_of parameter is given, returning a list of dicts with direction, predicate, the counterparty, and a current flag (true when valid_to is NULL). Invalidating a fact (invalidate) finds all open triples matching the subject/predicate/object and sets their valid_to to the given ended date (defaulting to date.today()). All mutations run inside with conn: transactions for atomicity.

Graph traversal directions

query_entity supports three directions: outgoing returns facts where the entity is the subject (entity→?), incoming returns facts where the entity is the object (?→entity), and both combines them. The implementation runs two separate SQL queries with a LEFT JOIN to entity names, one per direction, and includes the counterparty’s name (obj_name or sub_name) so the full relationship context is preserved for traversal.

Integration with fact-checking and disambiguation

The KG is the ground truth for fact_checker.py, which detects contradictions (relationship_mismatch, stale_fact) and name confusions (similar_name) by comparing incoming text against stored facts. seed_from_entity_facts bootstraps the graph from hand-curated ENTITY_FACTS (used in tests). The validator sanitize_kg_value permits punctuation and natural-language entity names — unlike sanitize_name for wings and rooms — supporting rich descriptions such as 'Alice (birth 1950)' → 'child_of' → 'Elizabeth (deceased 1985)'.

Stats and timeline

stats() returns total entities, total triples, current_facts (valid_to IS NULL), expired_facts, and the list of all predicate types; it backs tool_kg_stats and test assertions. timeline() returns up to 100 facts in chronological order (ordered by valid_from, NULLs last), optionally scoped to one entity’s incoming and outgoing edges, for narrative reconstruction and auditing.

⚡ Performance

Timeline queries are capped at LIMIT 100 (knowledge_graph.py:476). This is a sane default for interactive use, but timelines with more than 100 entries are silently truncated — there is no pagination, so a denser timeline needs a follow-up query or an API change.

Key concepts

Triple (RDF-style)
A fact expressed as subject→predicate→object (e.g. 'Alice' → 'works_at' → 'Acme Corp'). The core KG unit; predicates are normalized to lowercase with underscores.
Validity window
Optional valid_from/valid_to timestamps defining when a fact is true. Both accept ISO-8601 dates (YYYY-MM-DD) or canonical UTC datetimes (YYYY-MM-DDTHH:MM:SSZ). NULL means unbounded; values are inclusive on both ends.
Temporal query (as_of)
A query parameter returning only facts valid at a specified instant. Date-only queries like as_of=2026-01-15 normalize to T00:00:00Z; the comparison logic handles both legacy date-only values and canonical UTC datetimes.
Invalidation
Closing a fact by setting its valid_to date. The original triple with NULL valid_to is updated to an ended timestamp; no rows are deleted, preserving the audit trail and time-travel queries.
Entity disambiguation
Person/project/concept nodes identified by lowercase-slugified names (entity_id). The registry in entity_registry.py and fact_checker.py detect duplicates and confusion; the KG enforces deterministic lookups via this slug. See the Entity System.
Provenance fields (RFC 002 §5.5)
Optional source_drawer_id, adapter_name, source_closet, and source_file track where a fact came from: the drawer that mentions it, the adapter that extracted it, or the file/closet it references.
Confidence score
A per-triple float (default 1.0) indicating certainty. Not yet used in ranking but reserved for future fact-assessment integrations and conflict resolution.
Timeline
A chronologically sorted view of facts for an entity or the whole KG, ordered by valid_from (NULLs last) and limited to 100 rows; useful for narrative reconstruction.

Implementation highlights

Temporal normalization via SQL CASE expressions. Rather than converting values in Python, the system normalizes in SQL (knowledge_graph.py:84–103), so the comparison runs at query time against the actual stored values, avoiding redundant conversions and keeping the Python path clean.

knowledge_graph.py:84 · date-only facts treated as full-day windows
def _sql_temporal_start_expr(column: str) -> str:
    """SQLite expression for comparing valid_from-style temporal values."""
    return (
        f"CASE WHEN length({column}) = 10 "
        f"AND substr({column}, 5, 1) = '-' "
        f"AND substr({column}, 8, 1) = '-' "
        f"THEN {column} || 'T00:00:00Z' ELSE {column} END"
    )

def _sql_temporal_end_expr(column: str) -> str:
    """SQLite expression for comparing valid_to-style temporal values."""
    return (
        f"CASE WHEN length({column}) = 10 "
        f"AND substr({column}, 5, 1) = '-' "
        f"AND substr({column}, 8, 1) = '-' "
        f"THEN {column} || 'T23:59:59Z' ELSE {column} END"
    )

Inverted-interval validation. Both add_triple and invalidate explicitly reject intervals where valid_to < valid_from (knowledge_graph.py:270–278 and 346–352). This matters because an inverted interval would be invisible to every as_of query — a silent failure that could hide data corruption.

knowledge_graph.py:270 · inverted intervals raise rather than vanish
if (
    valid_from is not None
    and valid_to is not None
    and _temporal_end_key(valid_to) < _temporal_start_key(valid_from)
):
    raise ValueError(
        f"valid_to={valid_to!r} is before valid_from={valid_from!r}; "
        "an inverted interval would be invisible to every KG query"
    )

Entity ID canonicalization. _entity_id (knowledge_graph.py:219) lowercases names, replaces spaces with underscores, and strips apostrophes, giving deterministic deduplication: 'Alice Smith' and 'alice_smith' resolve to the same ID.

Per-path singleton cache. The MCP server keeps _kg_by_path (mcp_server.py:176), one KG instance per palace path, and routes every operation through _call_kg (mcp_server.py:248), which acquires the KG lock to guarantee a single writer and consistent reads.

Schema migration for backward compatibility. _migrate_schema (knowledge_graph.py:180–194) detects and adds the source_drawer_id and adapter_name columns when missing, enabling RFC 002 §5.5 provenance without resetting existing palaces.

Duplicate detection on add. When adding a triple (knowledge_graph.py:298–303), the code checks for an identical subject/predicate/object with valid_to IS NULL; if found it returns the existing ID instead of inserting a duplicate, while still allowing the same fact under a different validity window.

⚠️ Gotcha

The KG does not enforce referential integrity at write time. Although the schema declares FOREIGN KEY (subject) REFERENCES entities(id), add_triple auto-creates missing entities on the fly (knowledge_graph.py:288–295). You can add a triple for entities that do not yet exist; the foreign key documents intent but is a soft constraint, enabling flexible triple creation without pre-populating the entity table.

⚠️ Gotcha

Predicates are always lowercased and space→underscore normalized at write time (knowledge_graph.py:282), so 'Child Of', 'child_of', and 'CHILD_OF' map to the same predicate. This is intentional (it simplifies predicate discovery), but callers expecting case to be preserved will be surprised.

Invalidation is idempotent — and why that’s deliberate

invalidate searches for triples with valid_to IS NULL (knowledge_graph.py:340). Called twice on the same fact, the second call finds no matches and does nothing — semantically correct but potentially surprising to callers expecting an error. The forgiving behavior aligns with CLAUDE.md’s “incremental-only” principle: operations are replay-safe.

knowledge_graph.py:328 · closing a fact, no-op on the second call
def invalidate(self, subject, predicate, obj, ended=None):
    """Mark a relationship as no longer valid (set valid_to date/time)."""
    sub_id = self._entity_id(subject)
    obj_id = self._entity_id(obj)
    pred = predicate.lower().replace(" ", "_")
    ended = sanitize_iso_temporal(ended or date.today().isoformat(), "ended")

    # Find all open (valid_to IS NULL) triples matching this fact
    rows = conn.execute(
        "SELECT id, valid_from FROM triples "
        "WHERE subject=? AND predicate=? AND object=? AND valid_to IS NULL",
        (sub_id, pred, obj_id),
    ).fetchall()
    # Update all matching rows; second call finds nothing -> safe no-op

Design decisions

SQLite over Neo4j or another graph database
CLAUDE.md’s “local-first, zero external API” principle. Neo4j (as Zep offers) needs a running server or a cloud subscription ($25/month+); SQLite is zero-infrastructure, file-based, and embedded. It trades native graph-traversal performance for simplicity — a fit-for-purpose call given MemPalace workloads (entity stars, not deep graph navigation). See Storage Backends.
Single coarse lock + WAL, not optimistic concurrency
The MCP server is single-process with background hooks running in threads. A coarse lock is simpler and sufficient; fine-grained locking would add complexity for no benefit. WAL mode allows concurrent reads while a write holds the lock, and the 10-second timeout absorbs occasional contention from heavy indexing or search.
Normalize predicates at write time, not query time
Normalizing on insert means queries need no case-insensitive matchers. The downside (lost original casing) is acceptable because relationships are usually written by code, not user input, and semantic normalization (parent, parent_of, ParentOf → parent_of) is more valuable than fidelity.
Temporal comparisons in SQL CASE, not Python
Performance and correctness: normalization happens once per query, over the actual stored values, keeping the code path close to the data. Date-only facts are normalized just-in-time (00:00:00 for valid_from, 23:59:59 for valid_to), preserving the intent that a date spans the full day.
Invalidation updates the same row, not an insert
Audit trail and correctness: updating valid_to preserves the original triple ID and keeps a fact’s full lifetime visible in one row. Inserting a new “ended” row would force queries to UNION versions; an in-place update is simpler and matches RDF 4D semantics (fact + time range).

Data flow

Data moves through the KG in two directions. Ingestion (add_triple, add_entity, seed_from_entity_facts) is driven by miners (project mining via miner.py, conversation mining via convo_miner.py) through adapters carrying RFC 002 §5.5 provenance, and by fact_checker.py validations. The MCP server exposes tool_kg_add, tool_kg_invalidate, and tool_kg_query as the public interface.

Query operations (query_entity, query_relationship, timeline) are driven by fact-checkers validating incoming text, by CLI tools (kg-query, kg-list), and by search integration — note that searcher.py does not call the KG directly, but the KG is available for post-search enrichment. Output feeds back into fact_checker.py for contradiction detection and entity_registry.py for disambiguation.

Every operation flows through _call_kg in mcp_server.py, which acquires the singleton KG for the palace path and holds the lock during execution. Schema mutations (_migrate_schema) run once at initialization. Data persists in the SQLite file; nothing is cached in memory beyond the connection object.
