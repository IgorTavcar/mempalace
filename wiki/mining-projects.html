Project Mining

Turning a project directory of files into verbatim, searchable drawers.

Project mining scans a directory tree, detects file formats by extension and content, chunks text into drawers, applies virtual line numbering for locators, and stores them idempotently in the palace. The process is incremental: re-mining the same project never duplicates drawers — it upserts to the same storage rows, keyed by deterministic SHA-256 IDs. Gitignore rules, size limits, and chunk-cap safeguards prevent runaway ingest, while adjacent format extraction and mega-file splitting are siblings to the core miner, sharing chunking, entity detection, and room-routing logic.

How it works

Mining is a six-stage pipeline that runs per file and converges idempotently on re-runs. The entry point is process_file (miner.py:1268), orchestrated across a directory by scan_project. Each stage is read-time or reversible — drawers are stored verbatim, and every transformation (chunking, line numbering, closet generation) can be recomputed without touching the stored text.

Directory walk and file discovery

scan_project(project_dir) walks the filesystem recursively, respecting .gitignore rules and skipping known cache directories (SKIP_DIRS: .git, __pycache__, .venv, node_modules, etc.). Symlinks are detected and logged to stderr without being followed. Files are filtered by extension (READABLE_EXTENSIONS: .py, .md, .json, .go, .rs, …), and files over MAX_FILE_SIZE (500 MB) are silently dropped. The result is a deterministic, sorted list of paths ready for processing.

Per-file content routing and chunking

process_file() reads each file's bytes (utf-8 with errors='replace'), then routes it to a room via detect_room() (miner.py:425). Room detection is a four-tier priority: folder path matches room name/keywords > filename matches > keyword scoring in the first 2000 chars > fallback to general. Content is then chunked via chunk_text() using configurable CHUNK_SIZE (default 800), CHUNK_OVERLAP (128), and MIN_CHUNK_SIZE (50). Chunks break at paragraph or line boundaries when possible. Each chunk receives 1-indexed line numbers computed via str.count() to avoid O(n²) slicing on large files.

Incremental and idempotent drawer storage

Before writing, process_file checks file_already_mined(collection, source_file, check_mtime=True) (palace.py:714). This returns False — triggering a re-mine — when (1) no drawers exist for this file, (2) normalize_version is stale, or (3) the file mtime differs from the stored source_mtime. A re-mine first purges stale drawers (a delete where source_file matches), then upserts fresh ones in batched 1000-chunk transactions. Drawer IDs are deterministic (SHA-256 of source_file + chunk_index), so re-running idempotently upserts to the same rows without duplicating — and parallel re-mines converge on correct state without race conditions.

Metadata enrichment: dates, entities, halls, line ranges

For each chunk, _build_drawer_metadata() extracts a content_date via a five-tier hierarchy: filename (ISO or natural language) → YAML frontmatter date/created/published → content-body scan (ISO, slash dates, dateutil) → mtime. Entities come from _extract_entities_for_metadata() (miner.py:845): known entities from ~/.mempalace/known_entities.json matched case-insensitively, plus capitalized words appearing 2+ times in the first 5000 chars, filtered through a COCA stoplist. A hall is detected via keyword scoring (emotional, technical, family, general). All of this is packed into a single metadata dict per drawer — one drawer equals one embedding in ChromaDB. See the entity system for how the registry is populated.

Closet pointer generation (Tier 6a)

After all chunks are upserted, build_closet_lines() (palace.py:241) creates a compact, searchable index. It extracts topics (action verbs plus context, markdown headers), entities (nouns with 2+ occurrences), and quotes from the first ~CLOSET_EXTRACT_WINDOW chars. Each line is a pointer of the form topic|entities|[date:Lstart-Lend]|→drawer_ids. The date:Lstart-Lend segment (Tier 6a) is emitted only when drawer metadata carry both a line range and a content_date, letting retrieval jump to a line range without opening the whole drawer. Legacy 3-segment pointers are emitted when metadata is absent, preserving backward compatibility. The AAAK dialect documents this pointer grammar in full.

Post-mine graph construction

Once all files in a wing are processed, _compute_topic_tunnels_for_wing() links this wing to any other wing sharing a confirmed topic (from the user's known_entities.json registry). compute_hallways_for_wing() links entities (people, projects) co-occurring in drawers across the wing's rooms, and _compute_entity_tunnels_for_wing() materializes cross-wing tunnels from those hallway records. All three steps are fault-tolerant — exceptions are logged and never fail the mine — because they are derived analytics layered on top of completed drawer writes. The resulting structure feeds the temporal knowledge graph.

Key concepts

Drawer
A single chunk of verbatim text from a source file, stored with metadata (wing, room, line range, date, entities). The atomic unit of search in the palace.
Closet
A searchable index of pointers linking a source file to its drawers. Each pointer carries extracted topics/entities, Tier 6a date:line locators, and drawer IDs. Closets are scanned first; drawers are materialized on a search hit.
Virtual line numbering
Line numbers added at read time (not stored on disk) when a drawer is retrieved. Enables Tier 6a closet pointers to jump to specific line ranges within a drawer without rewriting the stored text.
Idempotency
Re-mining a file produces deterministic drawer IDs, so writes upsert to the same rows. The miner uses source_file + chunk_index + SHA-256 to keep IDs stable across re-runs; mtime-based detection re-mines only if the file changed.
Room detection
Content-aware routing that assigns each file to a room by folder path (highest priority), filename, or keyword scoring in the first ~2000 chars. Falls back to general if no match.
Tier 6a content dating
Automatic date extraction from filename, YAML frontmatter, content body, or mtime — in that priority order. Populates content_date in drawer metadata for Tier 6a closet pointers.
Entity extraction for metadata
Tagging drawers with known-entity names (from ~/.mempalace/known_entities.json) plus capitalized words appearing 2+ times in the first 5000 chars, filtered through a COCA common-words list to drop noise.
Hall detection
Content-type categorization (emotional, technical, family, etc.) based on keyword scoring across the first 3000 chars. Rooms organize by topic; halls organize by feeling/type.

Implementation highlights

Deterministic drawer IDs for idempotency. The drawer ID is a SHA-256 of source_file + chunk_index, stable across runs, so re-mining upserts to the same ChromaDB rows without duplicates. No version field or timestamp lives in the ID itself.

miner.py:1380 · deterministic drawer ID from source_file + chunk_index
drawer_id = f"drawer_{wing}_{room}_{hashlib.sha256((source_file + str(chunk['chunk_index'])).encode()).hexdigest()[:24]}"
💡 Insight — IDs are file+chunk, not timestamps

Because IDs derive from source_file + chunk_index, re-runs idempotently upsert without version fields or UUID tracking. A file moved to a new path produces a different drawer ID (intentional — it is a different source). The trade-off: renaming or relocating a source leaves the old drawers orphaned until explicitly purged. That is acceptable because drawers carry source_file metadata for retrieval.

Mtime-based dirty tracking without per-file state. source_mtime is stored in drawer metadata (miner.py:1224) and compared against os.path.getmtime(source_file) with a tolerance below 0.001 seconds, so filesystems with sub-millisecond precision still detect a genuine no-change re-run.

palace.py:772-777 · file_already_mined idempotency check with mtime tolerance
if check_mtime:
    stored_mtime = stored_meta.get("source_mtime")
    if stored_mtime is None:
        return False
    current_mtime = os.path.getmtime(source_file)
    return abs(float(stored_mtime) - current_mtime) < 0.001
⚡ Performance — the 0.001s mtime tolerance

Without this tolerance, slow filesystems or CI environments could trigger a redundant re-mine on every run even when the file was never modified. The tolerance accounts for filesystem timestamp precision (ext4 is nanosecond, NTFS is 100ns) and is a defense-in-depth measure against unnecessary embedding re-compute.

O(n) line counting for Tier 6a locators. Line ranges are computed with str.count('\n', 0, position) rather than splitting into a line list, avoiding O(n²) substring allocation on a 500 MB file with 50K chunks. The result is approximate (±1 at boundaries is acceptable), matching the closet-pointer-as-approximate-locator philosophy.

miner.py:552-553 · O(n) line counting without materializing a line list
line_start = content.count("\n", 0, start) + 1
line_end = content.count("\n", 0, end) + 1

Bounded memory via batched upserts. Chunks are accumulated and upserted in batches of DRAWER_UPSERT_BATCH_SIZE (1000) at miner.py:1375. Even a 50K-chunk file becomes 50 separate embedding forward-passes rather than one giant batch, preventing the embedding model from running out of memory and avoiding timeouts on Chroma/SQLite requests.

Per-file chunk cap with environmental override. MAX_CHUNKS_PER_FILE (50K) is resolved via _resolve_max_chunks_per_file() (miner.py:119) with precedence CLI override > MEMPALACE_MAX_CHUNKS_PER_FILE env var > module default. A cap of 0 disables the limit; negative values emit a warning and fall back to the default, preventing a typo-induced OOM on pathological files.

Gitignore matching with negation and directory-only rules. GitignoreMatcher._match_from_root() recursively matches patterns against path parts, supporting ** wildcards, anchored rules (/ prefix), and negation (! prefix). The last matching rule wins, reflecting gitignore semantics, and matching is cumulative across ancestor .gitignore files via an active_matchers list (miner.py:1471).

💡 Insight — re-check after the lock

Right before insertion, process_file re-runs the idempotency check under lock — another agent may have just finished mining the same file — so it returns early rather than redundantly writing.

miner.py:1340 · incremental upsert: re-check after lock, before insert
# Re-check after acquiring lock — another agent may have just finished
if file_already_mined(collection, source_file, check_mtime=True):
    return 0, room, None
Chunk boundary heuristics & the "rough 50% rule"
⚡ Performance — paragraph breaks over line breaks

chunk_text() (miner.py:472) looks for paragraph boundaries (\n\n) within the target range first, then line boundaries (\n), before breaking arbitrarily — keeping semantic units together. The "rough 50% rule" (break only if the newline is more than chunk_size//2 away) prevents pathological breaks on files with rare newlines.

Design decisions

Incremental-only append, never destructive rebuilds
CLAUDE.md mandates append-only ingest after the initial build: never destroy existing data to rebuild, and a crash mid-operation must leave the palace untouched. Deterministic drawer IDs and mtime-based dirty detection make safe re-runs possible — a crash mid-batch leaves completed batches intact, and a re-run resumes from the next uncompleted file. See architecture for how this principle propagates.
Virtual line numbering at read time, not stored on disk
Storing [N] prefixes in the drawer would couple presentation to storage, invalidate existing closet pointers on re-mine, and break idempotence. Read-time numbering (via render_with_line_numbers) keeps the drawer verbatim, lets Tier 6a date:Lstart-Lend pointers work, and stays backward-compatible — callers that ignore line numbers get the same string back with [N] prefixes added.
Closet pointers as compressed, searchable approximations
Closets are scanned (via FTS5) before drawers are opened. Each pointer extracts topics, entities, and quotes from the first ~5000 chars; the Tier 6a extension adds a date:Lstart-Lend segment so retrieval can jump to a line range. Pointers are intentionally approximate ("±2 off-by-one at boundaries is fine"); exact positional indexing is deferred to Tier 7. The search layer relies on this.
Room detection via path/filename/content, in that order
The priority (folder > filename > content) reflects user intent: a file in docs/frontend/ is routed to a frontend room even if its content never mentions it. Content-keyword scoring is the fallback, not the primary signal, preventing false positives from occasional mentions.
Format miner as a separate module, not integrated into miner.py
The codebase follows a miner-per-content-type pattern (scan → transform → chunk → store), and format_miner.py is a third instance of that shape. Separate modules give a smaller review surface, cleaner test isolation, and no risk of regressing the stable project/convo miners.
💡 Insight — the format miner is fully separate

Binary extraction (PDF, DOCX, RTF) could have been bundled into miner.py, but it lives in format_miner.py — a third parallel miner. The trade-off is some code duplication; the payoff is a smaller review surface and failure isolation, so a format-miner bug cannot affect project or conversation mining.

⚠️ Gotcha — RTF bypasses MarkItDown

MarkItDown 0.1.5 cannot convert RTF (it returns the raw \rtf1\ansi control codes unchanged). format_miner routes .rtf to striprtf instead (format_miner.py:387, verified empirically on 52 real RTF files). The per-format dispatch is invisible to callers — both transformers emit Markdown text that flows into the normal chunker.

Data flow

Project mining moves data through ten steps:

  • The CLI invokes mine(project_dir).
  • scan_project walks the filesystem, yielding paths filtered by extension, size, and .gitignore rules.
  • For each file, process_file reads bytes and checks file_already_mined (mtime-based idempotency).
  • detect_room routes the content to a room via path/filename/content scoring.
  • chunk_text splits content into 800-char chunks with 128-char overlap, computing virtual 1-indexed line ranges.
  • _build_drawer_metadata enriches each chunk with content_date (filename→frontmatter→body→mtime), known entities, capitalized-word frequency, and hall type.
  • Chunks are batched and upserted to the ChromaDB collection; deterministic SHA IDs ensure re-runs upsert to the same rows.
  • build_closet_lines extracts topics/entities/quotes from the first 5000 chars and creates pointer lines (legacy 3-segment or Tier 6a 4-segment).
  • Closet pointers are upserted to the closets collection, creating a searchable index.
  • Post-mine, _compute_topic_tunnels_for_wing links wings sharing confirmed topics, and compute_hallways_for_wing creates within-wing entity co-occurrence links.

All drawers are verbatim; every transformation (chunking, line numbering, closet generation) is reversible or read-time-only. A crash or re-run idempotently upserts to the same rows via deterministic IDs. See the palace model for how drawers, closets, halls, and tunnels relate, and storage backends for where the rows actually live.
