MemPalace

Local-first AI memory — verbatim storage, pluggable retrieval, ~96.6% R@5 with zero API calls.

MemPalace is a memory system for AI agents and the humans who work with them: it stores every word you share verbatim, indexes it as a spatial “memory palace” of wings, rooms, and drawers, and retrieves it with hybrid semantic + keyword search — all on your own machine, no API key required. It never summarizes, never paraphrases, and never phones home; the index is structured so searches can be scoped, but retrieval stays unstructured enough to surface a half-remembered conversation from a vague query. This wiki is a deep, cross-linked map of how the whole thing works — written for humans browsing the architecture and for agents grepping for the exact module, symbol, and line that does the thing. 💡 The core idea

MemPalace separates storage from retrieval: content is stored verbatim in drawers (never lossy), indexed by a structured symbolic layer (AAAK closets: entities, topics, quotes), and pulled back by unstructured hybrid search (vector + BM25). The index is a ranking signal, never a gate — a weak or missing pointer can only help a search, never hide a drawer — which is why 100% recall is the design requirement rather than a side effect. Store it structured, find it unstructured.

Design principles

These come straight from CLAUDE.md and are described there as non-negotiable — every PR, feature, and refactor must honor them. They are the constitution that every other page enforces in code.

Verbatim always
Never summarize, paraphrase, or lossy-compress user data. The system searches the index and returns the original words — whitespace, code formatting, and all. This is the foundational promise; see drawers.
Incremental only
Append-only ingest after the initial build. Never destroy existing data to rebuild — a crash mid-operation must leave the existing palace untouched. Re-mining a file deletes only that file’s stale drawers, then inserts fresh ones. See project mining and maintenance.
Entity-first
Everything is keyed by real names, disambiguated by DOB, ID, or context. People matter more than topics — the entity system and knowledge graph embody this.
Local-first, zero external API by default
All extraction, chunking, embedding, and LLM-assisted refinement runs on your machine using local runtimes (Ollama, LM Studio, llama.cpp). External providers are BYOK only — never required, never a silent fallback. See LLM integration.
Performance budgets
Hooks under 500 ms; startup injection under 100 ms. Memory should feel instant, so the hooks and the wake-up stack are tuned to stay off the critical path.
Privacy by architecture
The system physically cannot leak your data because it never leaves your machine — no telemetry, no phone-home, no external dependency for core operations. See security & privacy.
Background everything
Filing, indexing, timestamps, and pipeline work happen via background hooks. Nothing interrupts the conversation, and zero tokens are spent on bookkeeping in the chat window — roughly USD 1 saved per session.
⚡ Why “background everything” matters

In earlier versions the diary write fired in the chat window, re-transmitting the same blocks every turn at about USD 1.13 per session. Moving filing, timestamping, and palace writes into background hooks dropped that to zero — the content never enters the context window at all. Performance budgets (hooks < 500 ms, injection < 100 ms) keep memory invisible and instant.

🔒 Privacy is structural, not a setting

There is no “cloud sync” toggle to forget to turn off. Core operations — mining, embedding, search, the knowledge graph — run entirely on localhost, so the system cannot exfiltrate data it never sends. External LLMs are an explicit, per-use BYOK choice that triggers a privacy warning, never a silent default. See Security & Privacy.
