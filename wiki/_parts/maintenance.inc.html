Cross-cutting

Repair, Sync & Maintenance

Keeping a long-lived palace consistent, deduplicated, and recoverable.

Seven modules provide incremental-only Palace maintenance. repair.py detects and fixes HNSW index divergence and SQLite corruption behind an extraction-cap guard; sync.py prunes gitignored files using the same matchers as mining; migrate.py rebuilds Palaces across ChromaDB versions; exporter.py streams markdown with symlink safety; dedup.py consolidates near-identical drawers by cosine distance; spellcheck.py auto-corrects user messages while preserving technical terms; and sweeper.py catches message-granular content that file-level miners dropped. Every critical operation is crash-safe and honors the never-destroy promise.

How it works

All maintenance operations obey a single incremental-only invariant: they append new data or delete explicitly-marked corrupt entries, but never overwrite existing correct rows. A crash mid-operation leaves intact data untouched. Each module reads through the ChromaBackend and, where the API is unsafe, drops to direct SQLite access for recovery.

Repair: index health & divergence recovery

repair.py offers four tiers: status (read-only health check comparing SQLite row count vs HNSW element count), scan (identify unfetchable drawer IDs), prune (delete only corrupt IDs), and rebuild (extract all via the ChromaDB API, back up only chroma.sqlite3, delete+recreate the collection with correct settings, re-upsert). Three independent corruption signals are watched:

  • HNSW capacity mismatch — a stale max_elements setting reports less capacity than there are SQLite rows, eventually triggering segfaults.
  • Extraction vs SQLite ground-truth divergence — the extraction-cap guard (issue #1208).
  • Poisoned max_seq_id — a corrupt row holding ~1.23e18, silently suppressing queue writes; un-poisoned non-destructively before rebuild.

The backup strategy backs up only chroma.sqlite3, not the bloated HNSW files, so recovery stays fast even on terabyte-scale blob corruption. The FTS5 full-text index is atomically rebuilt post-repair via _vacuum_and_rebuild_fts5 without touching embeddings, reclaiming freed pages with VACUUM.

Sync: gitignore-aware drawer pruning

sync.py removes drawers whose source files are now gitignored, deleted, or moved out of project scope. It reuses the exact GitignoreMatcher infrastructure that miner.py uses on ingest, so files blocked at mining are also pruned at sync. It holds mine_palace_lock for the entire classify+apply window to see a consistent snapshot, and always preserves registry rows (_registry room / _reg_* prefix) to avoid re-chunking unchanged transcripts.

  • Project roots are auto-detected from drawer metadata (walk up to .git or .gitignore), then matched deepest-first to avoid over-pruning nested repos.
  • When source-file drawers are deleted, matching AAAK closet entries (keyed by source_file) are purged too.

Migrate: cross-version palace recovery

migrate.py rebuilds a Palace when the on-disk ChromaDB version diverges from the installed one. It extracts all drawers directly from chroma.sqlite3 (bypassing the API, which may fail on mismatched schemas), detects version via schema-shape inspection, and re-imports into a fresh Palace via add(). A pre-flight write round-trip test (upsert + get + delete) catches the 0.6.x → 1.5.x silent-drop failure mode where collections are readable but writes silently no-op. Direct extraction uses the same typed-column resolution as repair: string_value → int_value → float_value → bool_value.

Exporter: bounded-memory markdown streaming

exporter.py streams drawers in paginated batches of 1000, writing markdown organized by wing/room. Memory stays proportional to batch size, not total Palace size, supporting multi-million-drawer exports in a single pass. The index.md is built from wing_stats accumulated during streaming, and wing/room names are re.sub'd to strip filesystem-unsafe characters and leading dots/spaces.

Dedup: near-identical drawer consolidation

dedup.py groups drawers by source_file, finds pairs with cosine distance below a threshold (default 0.15, ~85% similarity), greedily keeps the longest/richest version, and deletes the rest. It uses ChromaDB's built-in query() with distances — no external API calls. The threshold is cosine distance (lower = stricter), tunable to 0.10 for near-identical only or 0.35 for paraphrased content. Omitting wing= catches the same source_file duplicated across wings.

Spellcheck: precision auto-correction with preservation

spellcheck.py corrects user messages while preserving technical terms, URLs, CamelCase identifiers, ALL_CAPS, words with digits/hyphens, and known entity names from the EntityRegistry. A system word-list skip (via /usr/share/dict/words) prevents over-aggressive autocorrect, and edit-distance guards keep corrections within 2–3 edits of the original. The autocorrect library is lazily initialized and degrades gracefully to pass-through if missing. Correction is applied only at user-message boundaries (lines starting with >).

Sweeper: message-granular ingest with idempotent dedup

sweeper.py ingests Claude Code .jsonl transcripts message-by-message (user + assistant), bypassing the file-level chunking of the conversation miners. A per-session cursor (max timestamp of prior sweeper-written drawers) skips already-ingested messages; at the cursor boundary it re-upserts via a deterministic ID (sweep_SESSION_UUID) so a crash mid-sweep is recovered on the next run. A pre-flight existence check (get(ids=...)) keeps the added-vs-already-present metrics honest. Each message-drawer is ~1–5 KB with no aggregation caps.

Key concepts

Incremental-only invariant
Maintenance appends new data or deletes explicitly-marked corrupt entries, but never overwrites existing correct data — a crash mid-operation leaves intact rows untouched.
Extraction-cap guard (issue #1208)
Safety check in repair.py::check_extraction_safety that aborts rebuild when the extracted drawer count (via the ChromaDB API) falls short of the SQLite ground-truth count, preventing silent data loss.
HNSW capacity divergence
Stale max_elements in HNSW metadata causes it to report less capacity than there are SQLite rows, eventually triggering segfaults — detected via hnsw_capacity_status and fixed by rebuild.
Poisoned max_seq_id
A SQLite max_seq_id row corrupted by a shim misfire, holding a ~1.23e18 integer that silently suppresses queue writes; repaired via heuristic (collection MAX) or sidecar restoration.
Crash-safe upsert pattern
Deterministic drawer IDs (e.g. sweep_SESSION_UUID) that let a re-upsert idempotently dedupe on reruns, making sweeper and other ingest paths resumable after failure.
Gitignore-aware sync
sync.py uses the same GitignoreMatcher infrastructure as miner.py, so files excluded from mining are also removed from the Palace during sync if they become gitignored.
FTS5 virtual table rebuild
The SQLite full-text-search index can drift after multiple collection deletes; repair.py::_vacuum_and_rebuild_fts5 atomically reconstructs it without touching row data.
Symlink defense-in-depth
exporter.py::_safe_open_for_write uses O_NOFOLLOW on POSIX and pre-checks os.path.islink on Windows to stop pre-placed symlinks from redirecting writes to system directories.

Implementation highlights

The extraction-cap guard is the linchpin of the never-destroy promise. Before any destructive rebuild it cross-checks the chromadb extraction count against the SQLite ground truth and refuses to proceed if the API returned fewer rows than the database holds.

repair.py:397 · extraction-cap guard (#1208 prevention)
def check_extraction_safety(
    palace_path: str,
    extracted: int,
    confirm_truncation_ok: bool = False,
    collection_name: Optional[str] = None,
) -> None:
    """Cross-check that extracted matches the SQLite ground truth."""
    sqlite_count = sqlite_drawer_count(palace_path, collection_name)
    cap_signal = extracted == CHROMADB_DEFAULT_GET_LIMIT
    if sqlite_count is not None and sqlite_count > extracted:
        loss = sqlite_count - extracted
        pct = 100 * loss / sqlite_count
        message = (
            f"\n  ABORT: chroma.sqlite3 reports {sqlite_count:,} drawers but only {extracted:,}\n"
            "  came back through the chromadb collection layer..."
        )
        raise TruncationDetected(message, sqlite_count, extracted)
⚠️ The 67,580 vs 10,000 catastrophe

Issue #1208 showed a Palace with 67,580 drawers on disk but only 10,000 returned through the ChromaDB API (exactly CHROMADB_DEFAULT_GET_LIMIT). A naive rebuild would have silently destroyed 57,580 rows. The guard aborts and forces explicit operator acknowledgement (--confirm-truncation-ok) after independent verification — it never auto-overrides. There is even a weak signal: extracting exactly 10,000 rows when SQLite can't be cross-checked is suspicious enough to refuse.

Rebuilds use a two-phase live swap: stage into a temp collection first, then delete and recreate the live one, tracking a live_replaced flag so the recovery path knows whether to restore the backup or leave the Palace intact. If temp upserts fail before deletion, the original is untouched.

repair.py:189 · two-phase rebuild with live-swap safety
def _rebuild_collection_via_temp(
    backend, palace_path, all_ids, all_docs, all_metas, batch_size,
    collection_name=None, progress=print,
):
    temp_name = f"{collection_name}__repair_tmp"
    live_replaced = False
    try:
        temp_col = backend.create_collection(palace_path, temp_name)
        # ... stage into temp ...
        backend.delete_collection(palace_path, collection_name)
        live_replaced = True
        new_col = backend.create_collection(palace_path, collection_name)
        # ... refile from temp ...
        return rebuilt
    except Exception as exc:
        raise RebuildCollectionError(str(exc), live_replaced=live_replaced) from exc

The sweeper earns idempotence with deterministic IDs plus a pre-flight existence query so its added-vs-already-present metric stays honest even though upsert is itself idempotent.

sweeper.py:229 · deterministic ID + honest metrics
def _flush():
    nonlocal drawers_added, drawers_already_present
    if not batch_ids:
        return
    try:
        existing = collection.get(ids=list(batch_ids), include=[])
        present = set(existing.get("ids") or [])
    except Exception as exc:
        logger.warning("sweeper: existence pre-check failed (%s); ...", exc)
        present = set()
    new_count = sum(1 for rid in batch_ids if rid not in present)
    already_count = len(batch_ids) - new_count
    collection.upsert(ids=batch_ids, documents=batch_docs, metadatas=batch_metas)
    drawers_added += new_count
    drawers_already_present += already_count

The exporter's symlink defense closes the TOCTOU window between an islink check and the open by using O_NOFOLLOW where available, falling back to a pre-check only on platforms that lack it.

exporter.py:44 · O_NOFOLLOW symlink defense
def _safe_open_for_write(path: str, mode: str, encoding: str = "utf-8"):
    o_nofollow = getattr(os, "O_NOFOLLOW", 0)
    if o_nofollow:
        flags = os.O_WRONLY | os.O_CREAT | o_nofollow
        flags |= os.O_APPEND if "a" in mode else os.O_TRUNC
        try:
            fd = os.open(path, flags, 0o600)
        except OSError as e:
            if e.errno == errno.ELOOP:
                raise ValueError(f"refusing to write: {path!r} is a symbolic link.") from None
            raise
        return os.fdopen(fd, mode, encoding=encoding)
    if os.path.islink(path):
        raise ValueError(f"refusing to write: {path!r} is a symbolic link.")
    return open(path, mode, encoding=encoding)
🔒 Sync refuses to run blind

In apply mode (dry_run=False), sync.py:224 refuses to run without an explicit wing= or project_dirs=, preventing an accidental full-Palace prune in a multi-project Palace. Auto-detection of project roots is only enabled in dry-run mode — safety by design. This aligns with the broader security-by-architecture posture.

💡 A sentinel that turns silent failure into a queryable state

When extracted drawers have None or {} metadata (from sparse historical writes), repair.py:150 coerces them to {"_repaired_empty_meta": True} to pass chromadb 1.5.x upsert validation. The sentinel is later discoverable via where={"_repaired_empty_meta": True} — a silent failure becomes an auditable, queryable marker.

💡 A heuristic that exploits float64 math

The poisoned-max_seq_id detector at repair.py:1342 uses a threshold of 1 << 53 (~9e15), the float64 exact-integer ceiling. Real embeddings_queue seq_ids stay below ~1e10, while the 0.6.x shim's misfire of int.from_bytes on b'\x11\x11' + ASCII digits yields ~1.23e18 — comfortably above the threshold. Clean values can never reach it, so the heuristic has effectively zero false positives.

⚡ Lexical cursor comparison, no date parsing

The sweeper's cursor (sweeper.py:147) returns max(timestamps) and compares with a plain lexical < cursor on ISO-8601 strings. Because ISO-8601 sorts lexically in chronological order, no parsing is needed — which is both fast and immune to timezone misinterpretation. The strict < (not <=) deliberately re-attempts messages at the cursor boundary in case an earlier same-timestamp message wasn't fully ingested.

Dedup & spellcheck edge cases

Greedy dedup keeps the longest. dedup.py:87 sorts a source group by document length descending and keeps a drawer only if it isn't too similar to one already kept. This is not optimal for lossy dedup (the shortest are often noise), but it is deterministic and recoverable.

Edit-distance guard varies by word length. spellcheck.py:206 allows max_edits of 2 for words ≤7 chars and 3 for longer. This blocks absurd one-edit jumps like a → the while still permitting sensible fixes like knoe → know.

Design decisions

Back up only SQLite, not HNSW files, during rebuild
HNSW binary files can grow to terabytes on corrupted Palaces; backing up only chroma.sqlite3 (the source of truth) makes recovery instant. The rebuild path never needs the old HNSW files, only the SQLite rows — squarely aligned with the incremental-only invariant.
Extraction-cap guard aborts rather than auto-overrides
Silently destroying 57,580 rows (as #1208 nearly did) is unacceptable, so the guard forces explicit user acknowledgement (--confirm-truncation-ok) after independent verification, honoring the never-destroy promise.
Sync holds the mine lock for the entire classify+apply window
A single snapshot across the classification and deletion passes prevents a race where a file is classified "gitignored" and then re-mined before deletion.
Spellcheck skips capitalized words entirely
Capitalized words are likely proper nouns or intentional emphasis; touching them risks corrupting names (Riley → riley) or domain terms (HTML → html). Leaving them alone is the only safe move.
Sweeper uses message-granular dedup, not file-level
File-level miners chunk at fixed byte sizes and don't track message boundaries. The sweeper catches message-level content and dedupes via deterministic ID, allowing re-run safety without re-chunking transcripts.

Data flow

Data moves through each module along a distinct path. Repair reads from the ChromaDB API and from SQLite directly (bypassing the API), backs up only SQLite, then reconstructs the collection via temp staging. Sync reads drawer metadata to classify by gitignore status, then deletes matching IDs in batches while holding the mine lock. Migrate extracts via raw SQLite reads when the API fails, re-imports into a fresh Palace at a temp path, then atomically swaps (with EXDEV copy+delete fallback and rollback guards). Exporter streams drawers in paginated batches, grouping by wing/room on the fly, writing markdown with symlink checks. Dedup batches drawers by source_file, queries cosine distances, and deletes marked duplicates. Spellcheck processes token-by-token, preserving technical terms and known entities. Sweeper parses .jsonl transcripts message-by-message, maintains per-session cursors, and upserts with deterministic IDs for idempotent reruns.
