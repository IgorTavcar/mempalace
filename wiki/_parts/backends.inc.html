Storage Backends

A pluggable storage interface — ChromaDB today, anything tomorrow.

MemPalace abstracts storage behind a minimal typed interface (BaseCollection, BaseBackend) so retrieval implementations can be swapped without touching mining, search, or repair code. ChromaDB is the reference implementation; third-party backends register via setuptools entry points. A typed result layer (QueryResult, GetResult) replaces Chroma's raw dicts, sophisticated HNSW health checks prevent native segfaults on diverged indices, and per-palace write locking serializes concurrent writes against ChromaDB's non-thread-safe HNSW graph.

How it works

The whole storage layer is roughly 2,500 lines split across four modules: the contract in base.py (382 lines), the ChromaDB implementation in chroma.py (1,602 lines), the registry.py resolver (189 lines), and the migrate.py recovery path (362 lines). Callers — miners, searchers, repair tools — only ever touch the abstract contract.

Interface-driven abstraction

The backend contract lives in base.py. BaseCollection defines six required, kwargs-only methods — add, upsert, query, get, delete, count — plus three optional hooks (update, close, health). BaseBackend is the per-palace factory: get_collection, close_palace, close, health, and an optional detect hook. This thin contract lets a miner call collection.upsert(documents=..., ids=...) without ever knowing whether data lands in ChromaDB, Postgres, or a custom store. A new backend inherits BaseCollection and BaseBackend, implements the methods, and announces itself via an entry point or an explicit register() call.

Typed results layer

Chroma returns raw dicts like {"ids": [[...]], "documents": [[...]]}. MemPalace wraps these in QueryResult and GetResult frozen dataclasses (base.py:129+) that enforce the outer-dimension-preserving spec and support attribute access (result.ids) as the primary API. Fields not requested via include= are populated with empty lists (never None) — except embeddings, which stays None if not requested. This typed boundary means all downstream code in search and repair receives consistent, predictable shapes.

ChromaDB health & recovery

ChromaBackend weaves three cold-start safety passes before any palace opens (chroma.py:1365-1392): _fix_blob_seq_ids patches the 0.6.x→1.5.x migration bug where seq_id remains a BLOB instead of migrating to INTEGER; quarantine_invalid_hnsw_metadata renames aside an unpickleable index_metadata.pickle to prevent a Rust-side SIGSEGV; and quarantine_stale_hnsw renames segments whose mtime has drifted beyond 300s or whose payload ratio exceeds 10×. These run once per palace per process (gated by a _quarantined_paths set), letting ChromaDB open safely on HNSW corrupted by cross-machine replication, partial restores, or mid-write crashes.

HNSW capacity divergence probe

ChromaDB flushes its HNSW index asynchronously, so sqlite_count and hnsw_count naturally diverge by up to 2×sync_threshold (chroma.py:522-606). The hnsw_capacity_status function probes both counts via low-level SQLite queries — deliberately avoiding the segment reader that could crash — then flags real divergence (>10% or >2×threshold) as status="diverged", letting search warn and fall back to BM25. This catches the issue #1222 failure mode (max_elements froze at 16K while SQLite held 192K) before a vector op segfaults. The probe itself never raises — a throwing probe would defeat its own purpose.

Registry & entry-point resolution

registry.py discovers backends at module load: available_backends() scans importlib.metadata.entry_points("mempalace.backends") and stores classes in a module-level _registry dict. get_backend("chroma") returns a cached singleton instance; resolve_backend_for_palace follows RFC 001 §3.3 priority — explicit flag > config value > env var > detect-from-disk > default "chroma". Tests and local dev call register("my_backend", MyBackendClass) to override, winning over entry points on a name conflict.

Per-palace write locking

ChromaCollection.upsert/add/delete wrap the underlying call in _write_lock (chroma.py:938-951), which acquires mine_palace_lock (in palace.py) when a palace path is set. This serializes MCP tool writes against mempalace mine CLI invocations, preventing the race that triggers HNSW corruption (#974/#965): when N copies of mine run concurrently, each drives parallel inserts that corrupt link_lists.bin. The lock is reentrant per thread, so the inner collection.upsert inside an already-locked mine pipeline does not re-acquire and self-deadlock.

Key concepts

BaseCollection
Abstract interface every backend must implement: add, upsert, query, get, delete, count, plus optional update/health/close. The per-collection read/write contract consumed by miners, searchers, and repair tools.
BaseBackend
Per-palace factory contract owning get_collection, close_palace, health, and an optional detect hook. Lightweight on construction (no I/O); connection is deferred to get_collection. Thread-safe for concurrent multi-palace access.
PalaceRef
Value object identifying a palace: id (cache key), optional local_path (filesystem), optional namespace (server-mode routing). Replaces legacy path-string arguments in the RFC 001 migration.
QueryResult / GetResult
Typed frozen dataclasses replacing Chroma's raw dict returns. They preserve the outer query dimension even when hits are empty, include an optional dict-protocol shim for legacy callers, and leave the embeddings field None unless explicitly requested.
HNSW capacity drift
Divergence between the SQLite embedding count and the HNSW index element count. Signals missing or corrupt vector data; corrected by quarantine checks before open and by divergence probes that trigger fallback to BM25 search.
Collection metric invariant
Collections are created with hnsw:space=cosine for consistent cosine-distance similarity scoring. Legacy palaces missing this metadata silently use L2 distance, breaking downstream relevance interpretation.
Registry entry-point discovery
Backend implementations announce themselves via setuptools entry points under mempalace.backends, discovered once per process at module load. An explicit register() wins on name conflict.
ChromaDB version migration
A direct SQLite extraction path for palaces unreadable by the current chromadb version: it writes to a fresh palace, then performs an atomic swap. Automatic migration on 1.5.x+ makes manual migrate rarely needed except for downgrades.

Implementation highlights

Typed results with a dict-compatibility shim. _DictCompatMixin (base.py:105) supplies __getitem__, get, and __contains__ to QueryResult and GetResult so legacy code expecting the raw dict protocol (result["ids"], result.get("ids")) keeps working. New code MUST use attribute access; the dict shim is an explicit migration bridge scheduled for removal.

base.py:129-145 · QueryResult with outer-dimension preservation
@dataclass(frozen=True)
class QueryResult(_DictCompatMixin):
    """Typed return from ``BaseCollection.query``.

    Outer list dimension = number of query vectors / texts.
    Inner list dimension = hits per query (may be zero).
    """
    ids: list[list[str]]
    documents: list[list[str]]
    metadatas: list[list[dict]]
    distances: list[list[float]]
    embeddings: Optional[list[list[list[float]]]] = None

HNSW bloat prevention via sync-threshold tuning. _HNSW_BLOAT_GUARD (chroma.py:127) sets hnsw:batch_size and hnsw:sync_threshold to 50_000 at collection creation (vs. chromadb's default of 1000). This breaks the resize + persist-dirty feedback loop that bloated link_lists.bin into hundreds of GB of sparse files on large mines — empirically validated on a 39K-drawer rebuild in 2026-04 with no segfault. The guard is applied at the moment of collection creation:

The write lock is a thin context manager. When a palace path is configured, every write enters mine_palace_lock; when it is None (a bare ChromaCollection built outside ChromaBackend) it yields immediately.

chroma.py:938-951 · write-lock context manager
@contextlib.contextmanager
def _write_lock(self):
    """Acquire ``mine_palace_lock`` for the configured palace, if any.

    No-op (yields immediately) when ``self._palace_path`` is None.
    """
    if self._palace_path is None:
        yield
        return
    from ..palace import mine_palace_lock
    with mine_palace_lock(self._palace_path):
        yield

Entry-point discovery with explicit override. _discover_entry_points (registry.py:56) loads declared backends exactly once, skipping any name already registered explicitly, and rejecting entry points that do not resolve to a BaseBackend subclass.

registry.py:56-91 · entry-point discovery, explicit registration wins
def _discover_entry_points() -> None:
    """Load entry-point-declared backends once per process."""
    global _discovered
    if _discovered:
        return
    with _lock:
        if _discovered:
            return
        eps = metadata.entry_points()
        group = (
            eps.select(group=_ENTRY_POINT_GROUP)
            if hasattr(eps, "select")
            else eps.get(_ENTRY_POINT_GROUP, [])
        )
        for ep in group:
            if ep.name in _explicit:
                continue  # explicit registration wins
            cls = ep.load()
            if not isinstance(cls, type) or not issubclass(cls, BaseBackend):
                continue
            _registry.setdefault(ep.name, cls)
        _discovered = True
🔒 Security

HNSW metadata is read without ever deserializing untrusted disk state. _segment_appears_healthy (chroma.py:161) only sniffs the pickle's start byte (0x80 PROTO marker) and end byte (0x2e STOP) to distinguish a complete write from truncation or zero-fill. When deserialization is genuinely needed, _SafePersistentDataUnpickler (chroma.py:375) is a whitelist-only Unpickler that permits a single class — chromadb.segment.impl.vector.local_persistent_hnsw.PersistentData — and raises UnpicklingError for anything else. The file is user-owned, but the byte-sniff plus whitelist is defense-in-depth against arbitrary code execution.

💡 Insight

The HNSW link/data ratio is a corrupted-index canary (chroma.py:36). When link_lists.bin grows more than 10× larger than data_level0.bin, the graph is structurally unsound and Chroma can segfault in native code even if the mtime looks fresh and index_metadata.pickle is valid. Healthy palaces sit below 1×; issue #1218 saw 300×. The ratio check is intentionally not gated by mtime — a 10× misbalance is unsafe regardless of recency — catching corruption that filesystem timestamps alone would miss.

Migration verifies a real write roundtrip. collection_write_roundtrip_works (migrate.py:174) upserts a probe record, confirms it appears in get, deletes it, and confirms the deletion. This catches the silent-noop failure mode where some 0.6.x→1.5.x migrations leave a collection readable but write/delete no-op — a count() probe alone would miss it, falsely reporting "no migration needed" when a rebuild is actually required. When a palace is wholly unreadable, extract_drawers_from_sqlite (migrate.py:52) reads embeddings and metadata via raw SQL, bypassing the chromadb API entirely.

Inode + mtime cache invalidation

ChromaBackend._client (chroma.py:1276) detects palace rebuilds (repair / nuke / purge) by comparing (inode, mtime) of chroma.sqlite3 against cached freshness state. An inode change triggers a _quarantined_paths discard so cold-start quarantines re-run; an mtime change (or a 0→nonzero transition) forces a client rebuild. FAT/exFAT filesystems that report inode 0 fall back to mtime-only comparison with a 0.01s epsilon to tolerate filesystem granularity.

Design decisions

Kwargs-only signatures for all collection methods
RFC 001 §1 eliminates positional-arg mistakes (e.g. swapping ids and documents) and makes callers self-documenting. Every backend enforces this at the interface layer; chromadb's legacy positional API is adapted only inside the ChromaCollection translate shim.
Typed results as the canonical return type, with a dict shim for migration
Attribute access (result.ids) is the primary API; dict access is a temporary bridge for callers predating RFC 001. The frozen dataclass prevents accidental mutation and eases testing, and the outer-dimension rule guarantees predictable shapes downstream.
Per-palace write locking in ChromaCollection, not the backend
RFC 001 §2 makes backends thread-safe for concurrent multi-palace access, but each palace's HNSW writer must be serialized. Locating the lock at the collection (where writes happen) keeps the concurrency model local and makes it clear that MCP and mine can coexist; reentrant per-thread locking prevents self-deadlock inside the mine pipeline.
Entry-point registry with explicit-registration override, no auto-loading
RFC 001 §3.2: backends are opt-in via entry_points or explicit register() — never auto-discovered from filesystem or environment. Explicit registration wins on conflict, keeping tests deterministic; late loading via importlib.metadata makes third-party backends available without becoming hard dependencies.
Cold-start quarantine runs once per palace per process
Safety checks like quarantine_stale_hnsw are idempotent but expensive (mtime + payload-ratio scans on every segment). The _quarantined_paths gate defers them to the first get_collection call, or after an inode change (rebuild), balancing safety against runtime thrash on long-running daemons.
⚠️ Gotcha

Reentrant locking prevents self-deadlock on the mine pipeline (chroma.py:938). The pipeline calls get_collection → ChromaCollection.upsert, which tries to acquire the same mine_palace_lock. Without a per-thread holder set in palace.py, the inner upsert would block on a second flock (Linux fcntl locks are per file descriptor) and deadlock on a single thread. The fix is subtle: _mark_held/_is_held consult a thread-local set before attempting the flock, so reentrant calls yield immediately.

⚠️ Gotcha

Legacy palaces silently fall back to L2 distance when cosine is expected (chroma.py:1169). Collections created before hnsw:space metadata was mandatory use ChromaDB's default (L2/Euclidean). The searcher's cosine formula max(0, 1 - distance) then floors at 0 because L2 distances exceed 1.0. The mismatch is not caught at query time — it only surfaces as nonsensical relevance scores. searcher.py emits a stderr notice recommending repair rebuild-index, but the palace keeps running in degraded mode.

⚡ Performance

The divergence threshold scales dynamically with the sync threshold (chroma.py:567). The HNSW divergence floor is max(2000, 2×sync_threshold) because ChromaDB batches flushes at sync_threshold intervals (raised to 50K in PR #1191 to prevent link_lists.bin bloat). A fixed floor of 2000 would flag every actively-written palace as diverged once the unwritten tail exceeded 1K records. Scaling with sync_threshold lets the probe distinguish normal flush-lag from real corruption (issue #1222's 176K divergence).

Data flow

Ingestion (project miners, diary, conversation miners) acquires mine_palace_lock, calls get_collection(palace_path, create=True) on the default ChromaBackend instance, and writes via collection.upsert(documents=..., ids=..., metadatas=..., embeddings=...). The ChromaCollection adapter translates to Chroma's dict API, sanitizes metadata (coercing None → {_repaired_empty_meta: True}), and wraps the call in the lock context.

On read (search, repair status), callers invoke collection.query or collection.get; ChromaCollection translates the raw Chroma dicts into typed QueryResult/GetResult shapes. Health checks (hnsw_capacity_status, quarantine_stale_hnsw) probe SQLite and HNSW metadata directly, bypassing the segment reader, to detect divergence and corruption before control passes to ChromaDB's native code. Cleanup flows through close_palace (evicts the cached PersistentClient, releases file locks) or close (full backend teardown for shutdown).
