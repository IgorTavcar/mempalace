Search & Retrieval

Hybrid BM25 + vector retrieval tuned for 100% recall.

MemPalace fuses vector semantic search with keyword-based BM25 scoring and optional closet-boosting to approach perfect retrieval. The system reaches 96.6% R@5 with zero LLM, 98.4% R@5 on held-out data through the full hybrid pipeline, and optional Haiku reranking pushes that to 100%. The core idea: a weak semantic match can always be rescued by strong keyword overlap or temporal/preference signals, eliminating the pure-vector cold-retrieval problem. Vector candidate selection is the floor that always runs; every later step can only improve ranking, never suppress a result.

How it works

Search runs as a layered pipeline. A vector candidate floor always executes first; closet boosting, hybrid BM25 re-ranking, union candidate gathering, and drawer-grep enrichment each refine that floor without ever discarding a directly-matched drawer. The design rule from CLAUDE.md is blunt: 100% recall is the design requirement, and hybrid ranking is the mechanism.

Vector candidate selection (the floor)

Every search begins with drawer-direct vector retrieval via ChromaDB's HNSW index, over-sampling n_results×3 candidates before ranking. The query is embedded with the configured model (minilm or embeddinggemma), compared against all drawer embeddings in the requested wing/room, and candidates are collected with their raw cosine distances. This baseline always runs; subsequent ranking steps can only reorder, never suppress.

Closet-based ranking signal (optional boost)

If a closets collection exists, the system queries it separately with the same query and builds a per-source boost table. The top closet for a source file yields a 0.40 distance reduction, the second 0.25, down to 0.04 for rank 5. Boosts apply only to drawers from that source, and only when the closet distance ≤ 1.5 (a too-weak signal is ignored). The palace structure makes closets the index layer that ranks drawer retrieval — they reorder, never gate.

Hybrid BM25 + vector re-ranking

After candidate gathering, _hybrid_rank applies Okapi-BM25 to the full candidate-set text. IDF is computed locally over the candidates themselves (corpus-relative, not global), so discriminativeness reflects each term's prevalence within the re-rank pool. Vector similarity is computed as max(0, 1 - distance) into [0, 1]; BM25 is min-max normalized to [0, 1] within the pool so the two signals are commensurable. The final score is 0.6 * vec_sim + 0.4 * bm25_norm — weights favor semantic matching but give keyword overlap enough force to rescue semantically-distant exact matches.

Query sanitization and embedding

Before embedding, the query is cleaned by query_sanitizer.py to strip system-prompt contamination that occurs when AI agents prepend instructions to their search queries. A 4-step fallback (passthrough if ≤200 chars, question extraction, tail-sentence extraction, tail truncation) recovers the actual intent, lifting recall from 1% to 70–80% in worst-case scenarios. The cleaned query is then embedded.

Candidate strategy: union mode

With candidate_strategy='union', after vector selection the system also queries the SQLite FTS5 fulltext index with the same query, pulling top n_results×3 BM25-only candidates. These are merged into the re-rank pool (deduped by source file and chunk index) and re-ranked alongside vector results. Union mode catches keyword-strong but vector-distant documents (terminology guides, technical specs) that pure-semantic search misses, at the cost of one SQLite open + FTS5 MATCH per query.

Drawer-grep enrichment for closet hits

When a drawer is matched via closet boost and its source file spans multiple chunks, the system fetches all chunks from that source, finds the one with the highest query-term overlap, and returns it plus ±1 neighbors. This "drawer-grep" pattern solves the case where vector search lands on a list header but the actual matching content lives in the next chunk. Enrichment is transparent: the caller receives combined context without a follow-up fetch.

💡 Insight

MemPalace's zero-LLM baseline (96.6% R@5 on LongMemEval) beats Mem0's LLM-extracted memories by over 2×. Extraction loses context — when Mem0 distills "user prefers PostgreSQL" and discards the conversation, it loses why, the alternatives considered, and what was said before. MemPalace stores everything verbatim and lets search find it. Nobody published this result before because nobody measured raw verbatim retrieval against extraction systems.

Key concepts

Okapi-BM25
Probabilistic keyword matching that scores documents on term frequency and inverse document frequency (IDF), tuned with k1=1.5 and b=0.75 per standard conventions.
Cosine distance
Vector similarity metric in the [0, 2] range used by ChromaDB's HNSW index; 0 = identical, 2 = opposite. MemPalace interprets it as absolute distance (not relative-to-max) to keep ranking stable as candidates are added or removed.
Hybrid ranking
Convex combination of vector similarity (60%) and normalized BM25 (40%) applied at re-rank time: 0.6 * vec_sim + 0.4 * bm25_norm, then sorted.
Closet boost
Ranking signal where a matching closet (topic index layer) reduces the effective distance of drawers from its source file by 4–40% depending on closet rank, clamped to [0, 2] to preserve cosine invariants.
Candidate strategy
Policy for gathering candidates before hybrid re-rank: 'vector' (default) uses top n_results×3 from HNSW; 'union' also pulls BM25-only candidates from SQLite FTS5 to widen the pool.
Effective distance
The distance after closet boost: max(0.0, min(2.0, raw_dist - boost)), keeping the result in valid cosine range [0, 2].
Drawer-grep enrichment
When a closet-boosted match spans multiple chunks in a source file, the system selects the chunk with the highest keyword-term overlap and returns it plus immediate neighbors for context.
BM25-only fallback
SQLite FTS5-based search used when the HNSW vector index is corrupted or unloadable, enabling graceful degradation to keyword search without segfaulting the server.

Implementation highlights

BM25 corpus-relative IDF. IDF is computed over the candidate set itself, not a fixed corpus, so each query's re-rank pool carries its own term-discriminativeness scores. This is crucial for small pools where term prevalence differs from the overall palace.

mempalace/searcher.py:102 · corpus-relative IDF over candidates
idf = {term: math.log((n_docs - df[term] + 0.5) / (df[term] + 0.5) + 1) for term in query_terms}

Convex-combination scoring. After normalizing BM25 within the pool, the two signals merge with fixed weights — semantic-leaning but keyword-rescuable.

mempalace/searcher.py:162 · vector_weight=0.6, bm25_weight=0.4
scored.append((vector_weight * vec_sim + bm25_weight * norm, r))

Effective distance clamping. A strong closet boost (up to 0.40) can exceed the raw distance; without the clamp the subtraction goes negative, yielding similarity > 1.0 and inverting the sort so boosted results paradoxically rank last. The clamp preserves the cosine invariant [0, 2] and makes boosts monotonically improve ranking.

mempalace/searcher.py:903 · keep effective distance in [0, 2]
effective_dist = max(0.0, min(2.0, dist - boost))
⚠️ Gotcha

CLOSET_RANK_BOOSTS = [0.40, 0.25, 0.15, 0.08, 0.04] uses the closet's ordinal position, not its absolute distance, to choose boost magnitude (searcher.py:871). Narrative content produces closet distances clustered in the 1.2–1.5 range regardless of match quality, making absolute distance unreliable — rank is more stable. Distances > 1.5 bypass boosts entirely via CLOSET_DISTANCE_CAP.

Query sanitizer 4-step fallback. Escalating strategies recover the real intent from contaminated queries, with length guards (MIN_QUERY_LENGTH=10) and quote stripping at each step.

🔒 Security

When AI agents prepend system prompts (2000+ chars) to search queries, the embedding model represents the concatenated string as a single vector where the prompt dominates the question — recall silently drops from ~90% to 1% (query_sanitizer.py:9). The sanitizer's 4-step approach recovers to 70–80% worst-case. Not perfect prevention, but it eliminates the catastrophic recall cliff.

⚡ Performance

Vector similarity uses max(0, 1 - distance) — absolute distance, not relative-to-max (searcher.py:160). If similarity were (max_dist - dist) / max_dist, adding one very-close candidate would raise max_dist and reshuffle every other score. Absolute scoring guarantees that adding or removing a candidate cannot reorder the others, giving stable, predictable ranking.

Chunk-precise dedup & BM25-only fallback

Union dedup keys are (source_file_full, chunk_index) pairs (searcher.py:684–703), not filenames. A single source file may split into 10 drawers; BM25 might surface chunk 3 (high keyword match) while vector found chunk 7 (high semantic match). File-level dedup would silently drop one — chunk-level dedup lets the same source contribute multiple perspectives to the re-rank pool.

BM25-only SQLite fallback (searcher.py:408–635): when vector_disabled=True (HNSW diverged), search routes to _bm25_only_via_sqlite, reading directly from chroma.sqlite3 via ChromaDB's FTS5 trigram index. Tokens < 3 chars are skipped (trigram limitation), and it falls back to recency-window then id-ordered queries if FTS5 fails — search never crashes, even with a severely corrupted vector segment. See storage backends and maintenance.

💡 Insight

Chunk-precise dedup is why the same source file can appear multiple times in results from different retrieval paths — BM25 and vector each contribute their best-matching chunk rather than competing for one slot. This is deliberate context preservation, not duplication.

Design decisions

Hybrid ranking always runs, vector 60% / BM25 40%.
Pure vector retrieval fails on exact-match queries (directory listings, diffs, mechanical content that embeds as noise); pure BM25 misses semantic paraphrases. The 60/40 split favors embedding similarity but gives keyword overlap enough weight to rescue lexical matches. Grounded in the CLAUDE.md principle "100% recall is the design requirement" — hybrid is the mechanism.
Closets are a ranking signal, never a filter gate.
Closets are generated via regex extraction on narrative content, so they can be weak or incomplete. Making them a filter would create a "weak-closets regression" where poor extraction hides good drawer matches. Signal-only mode means directly-found drawers always appear; closets just reorder them — honoring the verbatim-always principle that nothing is thrown away.
BM25 corpus is the candidate set, not a fixed global corpus.
Computing IDF over the re-rank pool gives each query term-discriminativeness scores tuned to its context. A term rare in the full palace may be common in the top-30 results; local IDF makes scoring adaptive, works well for small pools, and is cheaper than maintaining global IDF.
Embedding device is configurable and falls back gracefully.
MemPalace must run on laptops without GPU. Requesting an unavailable accelerator (CUDA on a CPU-only machine) logs a warning and falls back to CPU rather than hard-failing. CLAUDE.md: "Local-first by default, never silently use an external API." See embedding.
Query sanitization happens before embedding; cleaning is logged, not exposed.
When contamination is detected the sanitizer logs a warning but returns the clean query without changing the caller's view of what was searched. This prevents silent surprises ("why did my search change?") while still rescuing recall — the original query is preserved, the returned results are accurate.

Data flow

Queries enter via search_memories() or the CLI search() function. If query length suggests contamination (>200 chars), query_sanitizer applies its 4-step extraction. The cleaned query is embedded through get_embedding_function() (minilm or embeddinggemma with device selection). Drawers are retrieved from ChromaDB via vector search (n_results×3 over-fetch) while closets are queried in parallel to build a boost lookup table. Each drawer is scored by (1) raw vector distance, (2) closet boost if applicable, and (3) effective distance clamped to [0, 2], yielding an initial ranking. If candidate_strategy='union', BM25-only candidates are pulled from SQLite FTS5 and merged with chunk-level dedup. _hybrid_rank then applies Okapi-BM25, normalizes to [0, 1], and recomputes final scores as 0.6*vec_sim + 0.4*bm25_norm. For closet-boosted hits spanning multiple chunks, drawer-grep enrichment selects the highest-keyword-overlap chunk plus neighbors and returns expanded context. Results are trimmed to n_results and returned with similarity scores, source metadata, and optional closet previews. If HNSW is unavailable, _bm25_only_via_sqlite provides graceful fallback using FTS5 directly. The MCP server and CLI are the primary callers.
